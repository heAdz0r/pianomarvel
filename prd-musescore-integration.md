# PRD: поиск и автозагрузка нот с MuseScore.com в Piano Marvel Uploader

Статус: черновик для обсуждения. Основано на живом реверс-инжиниринге
musescore.com 2026-07-20 (тестовая пьеса — "Interstellar – Hans Zimmer
Interstellar" авторства ChungusBob, score id **9901456**,
`https://musescore.com/user/54797562/scores/9901456`) под реальным
залогиненным аккаунтом пользователя (`adsprogis`) в обычном Chrome.

---

## 1. Проблема и цель

Сейчас инструмент (см. [architecture.md](architecture.md)) требует, чтобы
все 4 файла композиции (PDF, MusicXML, MIDI, Audio) уже лежали на диске —
их находит `server/fileMatcher.ts` по соседству с одним указанным файлом.
Ручной шаг "найти и скачать эти 4 файла с MuseScore" остаётся
неавтоматизированным и медленным.

**Цель:** добавить в локальный UI шаг «найди композицию на MuseScore» —
пользователь вводит название/автора, видит список результатов (как в
поиске musescore.com), выбирает нужную аранжировку, инструмент сам качает
PDF/MusicXML/MIDI/Audio под один и тот же базовый filename и передаёт их
дальше в уже существующий pipeline (`scoreAnalyzer` → форма → загрузка →
Learn Mode), без единого клика на самом musescore.com.

**Не цель этого PRD:** автоматизация покупки/оплаты (см. §6 — платные
эксклюзивы всё равно требуют существующей подписки пользователя), обход
любых ограничений доступа, массовый батч-скрапинг каталога.

## 2. Что уже подтверждено живым тестом

### 2.1 Поиск

`GET https://musescore.com/sheetmusic?text={query}` — обычная
server-rendered HTML-страница (не JSON API за отдельным XHR — за время
тестирования ни одного JSON-эндпоинта поиска в сетевых запросах не
всплыло). Страница поддерживает фильтры через боковую панель:
Instrument (Piano/Violin/...), Difficulty (Beginner/Intermediate/Advanced),
Score type (Official/Community), Format (Interactive/PDF), Ensemble и т.д.
— **[GAP]** точные query-параметры этих фильтров не сняты (не было
времени прокликать каждый чекбокс и посмотреть на URL/DOM); для MVP
можно обойтись без них — просто передавать `text=` и присвоить
`instrument=Piano` вручную позже, если понадобится.

Каждая карточка результата содержит: обложку, заголовок, аранжировщика,
инструмент/ансамбль, число страниц/частей, длительность, дату, число
просмотров/сохранений, рейтинг (звёзды + число голосов), бейдж сложности
(Beginner/Intermediate/Advanced), бейдж «★ Official» если это
официальная нота, и опциональный бейдж «PRO» у конкретного
аранжировщика/скора, означающий, что скачивание требует активной
подписки. Ссылка на карточку — прямой URL вида
`/user/{userId}/scores/{scoreId}` или `/sheetmusic/{slug}` (нужно
подтвердить оба варианта на разных карточках — **[GAP]**, не проверено
для всех типов результатов, только для целевого).

### 2.2 Страница ноты

`https://musescore.com/user/{userId}/scores/{scoreId}` — есть кнопки
**Download / Print / Save score / Share / Add to Set / Edit on desktop**,
а также выпадающие Instrument/Difficulty (не относятся к скачиванию,
это переключатели отображения партии в вьюере).

### 2.3 Модалка Download → 4 нужных формата

Клик по **Download** открывает модалку с 5 пунктами: **Musescore, PDF,
MusicXML, MIDI, Audio** (нам нужны все, кроме Musescore/.mscz). Каждый
пункт — не `<a href>`, а кнопка с JS-обработчиком.

Подтверждено кликами (с разрешения пользователя):

| Формат | Поведение | Файл получен |
|---|---|---|
| **MusicXML** | мгновенно, новая вкладка открывается и почти сразу закрывается сама | ✅ `interstellar-hans-zimmer-interstellar.mxl`, 12599 байт |
| **MIDI** | то же самое, мгновенно | ✅ `interstellar-hans-zimmer-interstellar.mid`, 13698 байт |
| **PDF** | новая вкладка **не закрывается сразу**, её заголовок — *"Preparing file of score … for you"*, URL: `https://musescore.com/score/download/generate?file_type=pdf&generation_type=download&score_id=9901456&ts=1784537165&ttl=86400&sgn={64-hex-подпись}` — то есть рендер PDF идёт асинхронно на сервере | **[GAP]** клик подтверждён, страница генерации подтверждена, но итоговое сохранение файла в этом сеансе не досмотрено до конца (см. §5 про диалог сохранения) |
| **Audio** (mp3) | ожидаемо тот же паттерн `generate?file_type=mp3...`, тоже вероятно асинхронный рендер (микс аудио) | **[GAP]** клик не успел зафиксировать URL из-за смены координат кнопки на странице между попытками — паттерн не подтверждён напрямую для audio, только по аналогии с PDF |

Общий вид эндпоинта генерации (подтверждено для `file_type=pdf`,
предполагается по аналогии для `mxl`/`midi`/`mp3` — для двух последних
скорее всего тот же URL, но резолвится настолько быстро, что вкладка
не успевает отрисоваться, отсюда мгновенное закрытие):

```
GET https://musescore.com/score/download/generate
    ?file_type={pdf|mxl|midi|mp3}
    &generation_type=download
    &score_id={scoreId}
    &ts={unix_timestamp}
    &ttl=86400
    &sgn={подпись, 64 hex-символа}
```

**[GAP] Как считается `sgn`.** Это не отдельный видимый сетевой вызов —
подпись подставляется JS-бандлом страницы в момент клика. Похоже на
серверный HMAC, закешированный в состоянии страницы при её загрузке
(вероятный источник — `GET /api/score/link?full_models=1&id={scoreId}`,
который точно улетает при заходе на страницу ноты, но его тело прочитать
не удалось: встроенный `javascript_tool` заблокировал `fetch()`/чтение
`window` на этом залогиненном домене как потенциальную утечку
cookie/query-данных — это ограничение инструментов текущей исследовательской
сессии, не самого MuseScore). **Практический вывод: не пытаться
конструировать `sgn` руками — см. §4, схема B полностью обходит эту
проблему, просто кликая настоящую кнопку в реальном браузере.**

Также при каждом клике на Download летит трекинг-пинг:

```
POST https://track.musescore.com/score_download.trc
     ?has_access=1&score_id={scoreId}&user_id={userId}
```

`has_access=1` — сервер уже на этом этапе подтверждает, что у аккаунта
есть право скачать именно этот скор (иначе, видимо, `has_access=0` —
не проверено на скоре, требующем покупки, **[GAP]**).

### 2.4 Аутентификация

Сам факт, что Claude in Chrome в этой сессии видел уже залогиненный
аккаунт `adsprogis` — значит это реальная сессия пользователя в его
обычном Chrome, не что-то поднятое автоматизацией. Для будущего
Bun-инструмента это означает то же самое, что уже сделано для
pianomarvel.com: логин **только вручную, один раз**, через видимое окно
настоящего Chrome (переиспользуя механизм из `server/browser.ts` и
`fixes/google-oauth-rejects-playwright.md`, если у пользователя вход на
MuseScore тоже через Google/Facebook OAuth — **[GAP]** не проверено,
каким методом залогинен текущий аккаунт: email/пароль или соцсеть).

Playwright persistent-профиль может держать cookies сразу для
**обоих** доменов (`pianomarvel.com` и `musescore.com`) одновременно —
можно переиспользовать тот же `.browser-profile/`, не заводя отдельный.

**[GAP] Статус PRO на этом аккаунте не подтверждён однозначно.** Меню
профиля показывало пункт «Upgrade subscription» (обычно так подписывают
апсейл-пункт независимо от текущего статуса) — не установлено, активна
ли сейчас именно платная подписка, хотя пользователь описывает аккаунт
как «PRO». Для скорингов с бейджем «PRO» у конкретного аранжировщика
(видно в поиске, напр. «Matteo248 PRO») скачивание форматов, скорее
всего, требует именно активной подписки — без неё модалка Download,
предположительно, покажет paywall вместо форматов (**не проверено**).

## 3. Юридический контекст (MuseScore Terms of Service)

Прочитан `https://musescore.com/legal/terms` (актуальная версия на
2026-07-20). Значимые для этой задачи пункты:

- **§6.3** — «Content received through the Service may be accessed for
  your **personal, non-commercial use only**». Скачивание нот для
  собственной практики через Piano Marvel — ровно personal use,
  укладывается в это ограничение.
- **§6.2** — пользователь обязуется не передавать скачанные файлы
  третьим лицам и не тиражировать Content «onto any physical medium,
  memory or device… beyond» предусмотренного сервисом использования.
  Наш кейс — один пользователь скачивает свою же лицензированную копию
  и загружает её в свой же обучающий аккаунт Piano Marvel; это не
  раздача третьим лицам, но здесь нет однозначной судебной ясности —
  фиксируем как приемлемый, но не «чистый» риск.
- **§6.4** — «You may not… **reverse engineer**, decompile,
  disassemble… the Service». Формально это пункт про сам сервис/софт
  (не про ноты), но именно то, чем является §2.3 выше (изучение
  `?server-method`-подобных внутренних URL). **Прямая имитация подписанных
  `generate`-URL руками — зона реального риска нарушения ToS.**
  Управление через настоящий клик в настоящем браузере (см. схему B,
  §4) — тот же принцип, что уже принят в architecture.md для
  Piano Marvel: не реверсить приватный wire-формат, а водить реальный UI.
- **§5.2–5.3** — запрет на действия, которые «disrupt, impair or
  interfere with» сервис, и на «probing/scanning» его уязвимостей.
  Явного запрета на автоматизацию/ботов текстом не встретилось, но
  дух пунктов — против скриптов, дёргающих сервис не так, как обычный
  пользователь. **Вывод: держать частоту как у одного человека** (одна
  пьеса за раз, по явному клику пользователя в локальном UI, не фоновый
  батч по сотням пьес).
- **§5.4** — прямой запрет использовать «Licensed Compositions» для
  любых ML/AI-целей (обучение моделей и т.п.). Наш сценарий — не про
  ML, просто личная загрузка в обучающее приложение для игры на
  пианино; не похоже, что подпадает, но стоит помнить, если скоуп
  когда-нибудь расширится.
- Официальный **MuseScore Developer API** существует:
  `https://developers.musescore.com/` требует Consumer Key по запросу на
  `api@musescore.com`. Это ToS-чистый путь, если понадобится
  предсказуемый/поддерживаемый доступ без риска блокировки аккаунта —
  но там **[GAP]** не изучено, покрывает ли он вообще поиск и скачивание
  готовых файлов (PDF/MXL/MIDI/Audio) для произвольных пользовательских
  скорингов, а не только официальный каталог — сайт `developers.musescore.com`
  не отдал контента при попытке автоматического fetch (пустой ответ),
  нужно смотреть вручную или писать на почту.

**Рекомендация:** реализовывать через управляемый реальным браузером UI
(схема B, ниже) — по духу и по риску это ближе всего к «человек кликает
мышкой, просто быстрее», а не к обходу защит сервиса. Явный
raw-HTTP-реверс подписанных `generate`-URL — не делать вообще, даже если
технически возможно воспроизвести.

## 4. Варианты архитектуры

| # | Подход | Плюсы | Минусы |
|---|---|---|---|
| **A** | Официальный Developer API (ключ по запросу) | Полностью ToS-чистый, стабильный | Неизвестный охват (может не отдавать пользовательские скоры/готовые файлы), нужно ждать ответ от MuseScore на email, требует отдельного апрува |
| **B** ⭐ | Playwright ведёт настоящую страницу musescore.com в уже залогиненном профиле: поиск через `/sheetmusic?text=`, клик по Download → нужный формат, файл забирается через `page.waitForEvent('download')` | Не нужно понимать `sgn`/подпись вообще — браузер сам всё резолвит; минимальный риск по ToS (действия неотличимы от ручных); переиспользует существующий `browser.ts`/паттерн Piano Marvel Learn Mode | Медленнее raw-HTTP; зависит от разметки страницы (как и вся текущая архитектура); генерация PDF/Audio асинхронна — нужен таймаут подольше |
| **C** | Прямой raw-HTTP на `.../score/download/generate?...&sgn=...` в обход браузера | Максимально быстро, без Playwright для этого шага | Требует знать, как считается `sgn` (не выяснено), явно попадает под §6.4 ToS «reverse engineer the Service», хрупко при любом изменении фронтенда |

**Рекомендация: схема B**, полностью в духе уже принятого решения по
Piano Marvel Learn Mode (architecture.md: «раз сырой API не поддаётся —
ведём реальный UI»). Схему C не реализовывать.

### Важное уточнение про диалог «Сохранить как» (снято в этой же сессии)

Во время тестирования в этой сессии клик по Download в **обычном личном
Chrome пользователя** (через расширение Claude in Chrome, не через
управляемый Playwright-профиль) дважды показал нативный диалог macOS
«Сохранить как», который недоступен инструментам этой сессии (они видят
только содержимое вкладки через CDP, а не нативные OS-оверлеи).

**Это не является блокером для самого Bun-инструмента.** Playwright,
когда сам поднимает браузер (`chromium.launchPersistentContext(...)`,
как уже делает `server/browser.ts`), управляет загрузками программно:

```ts
const downloadPromise = page.waitForEvent("download");
await page.click(/* нужный пункт формата в модалке Download */);
const download = await downloadPromise; // ждёт реальный клик + (для PDF/Audio) серверную генерацию
await download.saveAs(destPath);
```

Playwright настраивает поведение загрузок на уровне CDP при создании
контекста и **не показывает нативный OS-диалог** независимо от системной
настройки Chrome «Спрашивать, куда сохранять каждый файл» — тот диалог,
который мы видели, специфичен именно для того, как расширение Claude in
Chrome подключается к уже существующему профилю пользователя, а не для
того, как работает сам Playwright. Проверить это на практике — первый
шаг реализации (см. §7, риск R1).

## 5. Предлагаемый пользовательский флоу

1. В существующем UI (`src/App.vue`) перед полем «Файл композиции»
   добавляется переключатель/вкладка **«Искать на MuseScore»** рядом с
   текущим «Указать локальный файл».
2. Пользователь вводит запрос (например `Interstellar Hans Zimmer
   piano`), опционально фильтр «только Piano solo».
3. Бэкенд (`GET /api/musescore/search?q=...`) через Playwright открывает
   `musescore.com/sheetmusic?text=...`, парсит карточки результатов
   (заголовок, автор/аранжировщик, обложка, difficulty, инструмент,
   рейтинг, число голосов, `scoreId`/URL, бейдж PRO/Official) и отдаёт
   JSON-список на фронт.
4. UI показывает список карточек (как в самом MuseScore) — пользователь
   выбирает одну.
5. `POST /api/musescore/fetch { scoreId, formats: ["pdf","mxl","midi","mp3"] }`
   — бэкенд заходит на страницу ноты, для каждого формата кликает пункт
   в модалке Download и сохраняет файл под единым базовым именем
   (например `{slug}.pdf`, `{slug}.mxl`, `{slug}.mid`, `{slug}.mp3`) в
   рабочую папку загрузок.
6. Результат подаётся напрямую в уже существующий pipeline: не через
   fuzzy-поиск `fileMatcher.ts` (он не нужен — имена уже гарантированно
   совпадают), а как готовый объект `MatchedFiles`, сразу в
   `scoreAnalyzer.ts` → форму метаданных → `piano.ts` → (опционально)
   Learn Mode, как сейчас происходит для локальных файлов.
7. Если какой-то формат недоступен (скор запрещает скачивание МIDI/XML,
   или требует PRO, которого нет) — бэкенд возвращает частичный
   результат с явным списком «что не удалось и почему», и UI ведёт себя
   как сейчас для отсутствующих локальных файлов: предлагает «Указать
   вручную».

## 6. Данные и структура ответа поиска (черновая схема)

```ts
interface MuseScoreSearchResult {
  scoreId: string;
  url: string;               // https://musescore.com/user/.../scores/...
  title: string;
  arranger: string;          // ник/имя автора аранжировки
  thumbnailUrl?: string;
  instrument?: string;       // "Piano", "Solo Piano" и т.п.
  difficulty?: "Beginner" | "Intermediate" | "Advanced" | "";
  isOfficial: boolean;       // бейдж "★ Official"
  requiresPro: boolean;      // бейдж "PRO" у конкретного скора
  rating?: number;           // 0–5
  votes?: number;
  pages?: number;
  durationSeconds?: number;
}

interface MuseScoreFetchResult {
  scoreId: string;
  baseName: string;          // общий slug для всех файлов
  files: {
    pdf?: string;             // путь на диске или undefined
    mxl?: string;
    midi?: string;
    mp3?: string;
  };
  skipped: Array<{ format: string; reason: string }>; // напр. "requires PRO", "download disabled by uploader"
}
```

**[GAP]** Точные CSS-селекторы/DOM-структура карточек результата и
модалки Download не задокументированы построчно (аналог того, что
`server/scrape.ts` делает для формы Piano Marvel) — это первая задача
реализации: написать `bun run scrape:musescore --dry`, аналогичный
существующему `bun run scrape`, который один раз пройдётся по живой
странице и зафиксирует селекторы в код, а не держать их только в этом
PRD.

| R6 | Официальный Developer API (вариант A) может закрыть часть задачи легальнее и надёжнее, но неизвестен его охват | Написать на `api@musescore.com`, спросить: 1) доступен ли поиск по пользовательским нотам, 2) доступна ли выгрузка PDF/MusicXML/MIDI/Audio по id, 3) какие лимиты |

## 8. Итог

Технически задача решаема с приемлемым риском **только через схему B**
(реальный Playwright-браузер кликает настоящий UI musescore.com в уже
залогиненной сессии пользователя, забирая файлы через
`page.waitForEvent("download")`, без попыток воспроизвести подписанные
`generate`-URL руками). Схема C (прямой raw-HTTP) технически
любопытна, но осознанно отклонена — как по неизвестности `sgn`, так и
по прямому конфликту с §6.4 ToS. Параллельно стоит одним письмом
запросить официальный Developer API (`api@musescore.com`) — если он
покроет нужный сценарий, это самый чистый долгосрочный путь и его можно
будет включить как альтернативный backend без переделки UI (интерфейсы
`MuseScoreSearchResult`/`MuseScoreFetchResult` из §6 останутся теми же
независимо от того, какой backend их наполняет).
