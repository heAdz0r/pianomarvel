# PRD: Оптимизация, устойчивость состояния и QoL

Документ написан как пошаговая инструкция для исполнителя. Каждая задача содержит:
файл, фрагмент существующего кода для поиска, что именно изменить, чем проверить и
критерий приёмки. Задачи независимы, если не указано обратное, и могут делаться по
одной с отдельной проверкой.

---

## 0. Правила работы (обязательны для всех задач)

1. **Комментарии — на русском**, у изменённой строки/блока помечай суть правки
   комментарием. Так принято во всём проекте.
2. **Никаких тайм-аутов как механизма ожидания.** Ждать можно только состояние
   (DOM, localStorage, сетевой ответ). Тайм-аут допустим исключительно как аварийный
   потолок и обязан жить в `server/learning-config.ts` (`LEARN_TIMING`) с
   переопределением через env. Запрещены `waitForTimeout`, `setTimeout` как «дай
   странице устояться», фиксированные задержки между действиями.
3. **Никакого хардкода по произведениям.** Ни названий, ни имён композиторов, ни
   номеров тактов в условиях. Это проверяет тест `server/adaptive-guarantees.test.ts`
   — он упадёт, если нарушить.
4. **Инварианты Piano Marvel не меняются.** Chopped — только двуручные упражнения;
   Minced — копия Chopped плюс RH/LH; Whole — вся пьеса плюс руки; ровно три
   Summarize; Phrase непрерывно покрывают Whole. Подробности:
   `docs/adaptive-learning.md`.
5. **Обязательная проверка после каждой задачи** (все четыре команды должны быть
   зелёными):

```bash
bun test && bun x tsc --noEmit -p tsconfig.json && bun x vue-tsc --noEmit && bun run build
```

   Плюс `git diff --check` (не должно быть пробельного мусора).
   На момент старта в проекте **84 теста, 0 падений** — это базовая линия.
6. **Живой Piano Marvel не трогать** без явной просьбы пользователя. Все изменения
   проверяются юнит-тестами и корпусным аудитом:

```bash
bun run server/adaptive-corpus-audit.ts ~/Downloads/clocks-coldplay.mxl
```

7. **Файлы пользователя в `~/Downloads` не перемещать и не удалять** без явного
   предпросмотра и подтверждения (задача C5 описывает, как именно).
8. **Сервер запускается без watch.** После правок серверного кода процесс надо
   перезапускать (`bun run dev`), иначе в памяти живёт прежняя версия. Это важно при
   ручной проверке.

### Дефект, найденный при приёмке и исправленный

**`tickCount` расходился на 83 такта из 1484 (5.6 %).** После перевода
`profileMeasure` на нотную модель (D5) позиции стали считаться по `onset` в
четвертях, а не по целочисленному курсору в `divisions`. Накопление 1/3 (триоли
Moonlight) даёт `1.9999999999999998` вместо `2`, и `Set` считал одну позицию за две.
Значение уходит в Piano Marvel как `end_tick` (`server-method-162`), поэтому дефект
влиял на живое сохранение. Исправлено округлением позиций до 1e-6 доли четверти;
добавлен регрессионный тест «end_tick не удваивает позицию из-за накопления
триольных долей». После исправления `tickCount` совпадает с прежней формулой на всех
1350 тактах проверенного корпуса.

### Открытый вопрос вне PRD

`server/scoreAnalyzer.ts` получил MIDI-fallback и `DEFAULT_UPLOAD_TEMPO = 60` для
партитур без темпа. Это не входило в PRD и меняет **входные данные корпусного
аудита**: `analyzeScoreFile` больше никогда не возвращает `defaultTempo: undefined`,
поэтому подстановка `?? 100` в `adaptive-corpus-audit.ts` стала мёртвой, и две
партитуры (Karma Police, No Surprises) считаются на Slow = 36 вместо 60. Живой Learn
Mode это не затрагивает: там темп берётся из состояния страницы Piano Marvel
(`inferFastTempo`). Проверено: при Slow = 60 текущий код воспроизводит прежний
результат для обеих партитур побитово, то есть части B и D результат не изменили.
Рекомендация: в аудите брать темп независимо от значения по умолчанию для загрузки,
иначе базовая линия метрик молча меняется при правках загрузчика.

# ЧАСТЬ A. Устойчивость состояния и конкурентность

## A1. Один неудачный запуск браузера ломает сервер до перезапуска

**Приоритет:** критический. **Оценка:** 15 минут.

**Проблема.** В `server/browser.ts` промис запуска кешируется в переменной
`launching`. Если запуск упал (профиль занят другим Chrome, `SingletonLock`,
обновление Chrome), в `launching` остаётся **отклонённый** промис. Сброс есть только
в обработчике `c.on("close")`, до которого дело не дошло. Каждый следующий
`getContext()` падает с той же ошибкой, даже когда причина исчезла. Лечится только
перезапуском сервера.

**Найди в `server/browser.ts`** (функция `getContext`):

```ts
        ctx = c;
        c.on("close", () => {
          ctx = null;
          launching = null;
          if (loginState !== "waiting") loginState = "unknown";
        });
        return c;
      });
  }
  return launching;
}
```

**Замени на:**

```ts
        ctx = c;
        c.on("close", () => {
          ctx = null;
          launching = null;
          if (loginState !== "waiting") loginState = "unknown";
        });
        return c;
      })
      // CHANGED: неудачный запуск не должен запоминаться. Раньше отклонённый промис
      // оставался в `launching`, и каждый следующий getContext() падал той же ошибкой
      // даже после того, как причина (занятый профиль, обновление Chrome) исчезла.
      .catch((error) => {
        launching = null;
        throw error;
      });
  }
  return launching;
}
```

**Тест.** Добавь в `server/browser.test.ts` (файл существует) проверку идемпотентности
сброса. Прямой запуск Chrome в тесте не нужен — достаточно проверить сам инвариант на
изолированной копии логики: если это неудобно, ограничься ручной проверкой ниже и
напиши в отчёте, что автотест не добавлен и почему.

**Ручная проверка.**
1. Запусти сервер.
2. Создай файл-блокировку: `touch .browser-profile/SingletonLock` (если запуск и так
   падает — просто вызови любое live-действие при уже открытом отдельном Chrome).
3. Дёрни любое действие, требующее браузера → должно упасть.
4. Убери причину, дёрни снова → **должно заработать без перезапуска сервера**. До
   правки на этом шаге сохранялась та же ошибка.

**Критерий приёмки.** После устранения причины первого падения следующий вызов
`getContext()` создаёт контекст; перезапуск сервера не требуется.

## A2. Версия алгоритма в кеше статусов не поднята

**Приоритет:** критический. **Оценка:** 10 минут (плюс проверка).

**Проблема.** В `server/cache.ts` есть механизм инвалидации кеша статусов:

```ts
export const LEARNING_ALGORITHM_VERSION = "learning-strategies-v2";
```

Чтение идёт только по совпадающей версии (`getLearningStatuses`):

```ts
         FROM learning_status_cache
         WHERE algorithm_version = ?
```

Музыкальный алгоритм Adaptive был полностью переписан (восемь слоёв анализа, другие
границы), а версия осталась прежней. Из-за этого все пьесы, собранные старым
алгоритмом, показываются как `ok`, и пользователь не видит, что их надо пересобрать.

**Что сделать.**
1. В `server/cache.ts` замени значение на `"adaptive-musicxml-v3"`.
2. Рядом добавь комментарий-правило:

```ts
/**
 * Версия алгоритма сборки обучения. Кеш статусов читается ТОЛЬКО по совпадающей
 * версии, поэтому строку обязательно менять при любом изменении музыкальной логики
 * Adaptive или целевой схемы: иначе пьесы, собранные прежней логикой, продолжают
 * выглядеть исправными.
 */
export const LEARNING_ALGORITHM_VERSION = "adaptive-musicxml-v3";
```

3. Добавь тест в `server/cache.test.ts`: записать статус, затем прочитать —
   возвращается; и отдельно проверить, что строка версии непустая и отличается от
   `"learning-strategies-v2"` (защита от возврата назад по невнимательности).

**Критерий приёмки.** После правки `getLearningStatus(любой id)` для ранее собранных
пьес возвращает `undefined` → в таблице статус «не проверен», а не «ok».

## A3. Ручная проверка статуса конкурирует со сборкой той же пьесы

**Приоритет:** высокий. **Оценка:** 40 минут.

**Проблема.** Три независимых дефекта одного класса «побеждает последний писатель»:

1. Кнопка-refresh в строке пьесы не заблокирована во время сборки. Инспекция открывает
   ту же пьесу в persistent-контексте, пока задача правит её из изолированного, и
   читает полусобранное состояние.
2. `PianoCache.putLearningStatus` перезаписывает запись без сравнения времени: более
   старая инспекция, ответившая позже, затирает свежий результат сборки.
3. На клиенте `statuses[pieceId]` пишут два источника — watcher задачи и `checkStatus`
   — тоже без сравнения времени.

**Что сделать — 1 (клиент, блокировка).**
Найди в `src/components/PiecesMovement.vue` кнопку проверки статуса:

```
                    :disabled="checking[row.original.id] || checkingAll"
```

Замени на:

```
                    :disabled="
                      checking[row.original.id] ||
                      checkingAll ||
                      row.original.learningState === 'running' ||
                      row.original.learningState === 'checking'
                    "
```

И в `title` этой же кнопки добавь пояснение для состояния running: если пьеса
собирается, подсказка должна говорить «Идёт сборка — статус обновится сам».
Реализуй через тернарный оператор в атрибуте `title`.

**Что сделать — 2 (сервер, монотонность кеша).**
В `server/cache.ts` в начало `putLearningStatus` добавь проверку. Первый параметр
`query` — тип строки результата, второй — кортеж параметров; ровно так типизированы
соседние методы файла:

```ts
  putLearningStatus(status: LearningStatus, checkedAt = new Date().toISOString()): void {
    // CHANGED: монотонность по времени проверки. Инспекция и сборка пишут статус
    // независимо, и более старый ответ, пришедший позже, затирал свежий результат.
    const existing = this.db
      .query<{ checked_at: string }, [number, string]>(
        "SELECT checked_at FROM learning_status_cache WHERE piece_id = ? AND algorithm_version = ?",
      )
      .get(status.pieceId, LEARNING_ALGORITHM_VERSION);
    if (existing && existing.checked_at > checkedAt) return;

    // дальше — существующий INSERT ... ON CONFLICT, без изменений
  }
```

Сравнение строк ISO-8601 лексикографически совпадает со сравнением времени — объекты
`Date` создавать не нужно. `.get()` возвращает `null`, если строки нет, поэтому
проверка `existing &&` обязательна.

**Что сделать — 3 (клиент, монотонность).**
В `src/components/PiecesMovement.vue` заведи единственную точку записи статуса:

```ts
// CHANGED: статус пишут два источника — watcher задачи и ручная проверка. Более
// старый ответ, пришедший позже, не должен затирать свежий.
function applyStatus(pieceId: number, status: LearningStatus, stamp: string) {
  const previous = checkedAt[pieceId];
  if (previous && stamp < previous) return;
  statuses[pieceId] = status;
  checkedAt[pieceId] = stamp;
}
```

Замени на её вызовы оба места:
- в `checkStatus`: строки `statuses[piece.id] = data.status;` и
  `checkedAt[piece.id] = data.checkedAt;`
- в `watchLearningJob`: блок `if (current.status) { statuses[...] = ...; checkedAt[...] = ... }`

**Тест.** В `server/cache.test.ts` добавь: записать статус со временем `T2`, затем тот
же piece со временем `T1 < T2` — чтение обязано вернуть версию с `T2`.

**Критерий приёмки.**
- Во время сборки пьесы кнопка проверки статуса неактивна.
- Запись более старого статуса не затирает более свежий ни в SQLite, ни в UI.

## A4. Снимок storageState для изолированных lanes не обновляется

**Приоритет:** высокий. **Оценка:** 1 час.

**Проблема.** В `server/learning-workers.ts`:

```ts
async function prepareWorkers(): Promise<void> {
  if (storageState && (LEARN_CONCURRENCY === 1 || workerBrowser?.isConnected())) return;
```

`storageState` снимается один раз за процесс. Последствия:
1. Куки в снимке не обновляются: если сессия Piano Marvel продлилась или сменилась,
   lanes 1..N продолжают работать с прежними и падают на авторизации.
2. Снимок содержит `localStorage`, а значит ключ `slicingData` **всех пьес на момент
   снимка**. Изолированная lane стартует с устаревшим состоянием той пьесы, которую
   собирается перестраивать, и `readSlicingSnapshot` может вернуть прошлое состояние
   вместо фактического.

**Что сделать.**
1. Снимай `storageState` **перед каждой партией задач**, а не один раз. Простое и
   достаточное решение: инвалидировать снимок, когда он старше, чем последняя запись
   сессии, либо когда очередь пуста. Реализация: добавь модульную переменную
   `storageStateAt: number | null` и обновляй снимок, если
   `queue.running === 0 && queue.queued === 0` (то есть перед новой волной) — так снимок
   всегда свежий на старте волны и не дёргается между lanes одной волны.
2. **Вырежи из снимка `slicingData`** — изолированной lane он не нужен, страница
   гидратирует состояние с сервера, а устаревшая копия только вводит в заблуждение.
   Делай это на объекте снимка:

```ts
/**
 * Убирает из снимка ключ slicingData. Изолированная lane получает копию localStorage,
 * и прежнее состояние разбиения из неё выглядело бы актуальным состоянием пьесы.
 * Авторизация в снимке нужна, состояние вкладок — нет: страница получит его с сервера.
 */
function withoutSlicingData(state: StorageState): StorageState {
  return {
    ...state,
    origins: state.origins.map((origin) => ({
      ...origin,
      localStorage: origin.localStorage.filter((item) => item.name !== "slicingData"),
    })),
  };
}
```

3. Применяй `withoutSlicingData` там, где снимок передаётся в `newContext({ storageState })`.

## B1. Кеш разбора партитуры по пути и времени изменения

**Приоритет:** высокий (самая заметная экономия). **Оценка:** 40 минут.

**Проблема.** `analyzeScoreFile` (`server/scoreAnalyzer.ts`) на каждый вызов заново
распаковывает `.mxl` через внешний `unzip` (см. `readScoreXml`) и парсит весь XML. За
один прогон «скачал → привязал → собрал обучение» один и тот же файл разбирается 3–4
раза:

- `POST /api/pieces/:id/score-source` → `analyzeScoreFile`;
- `toScanLikeResult` в `server/musescore.ts` → `analyzeScoreFile`;
- `buildAdaptiveLearningPlan` → `readScoreXml`;
- корпусный аудит (если запускается) → снова оба.

**Что сделать.** Добавь в `server/scoreAnalyzer.ts` память по ключу
`путь + mtimeMs + size`:

```ts
// CHANGED: один и тот же файл разбирается несколько раз за прогон (привязка,
// метаданные для формы, план Adaptive). Ключ включает mtime и размер, поэтому
// перезаписанный файл читается заново, а повторный разбор того же — из памяти.
const xmlCache = new Map<string, { xml: string; analysis?: ScoreAnalysis }>();

function cacheKey(path: string): string {
  const stat = statSync(path);
  return `${path}:${stat.mtimeMs}:${stat.size}`;
}
```

Требования к реализации:
1. Кешируй результат `readScoreXml` (строку XML) и результат `analyzeMusicXml`
   (объект `ScoreAnalysis`) — оба по одному ключу.
2. Ограничь размер: не больше 24 записей, при переполнении удаляй самую старую
   (простой FIFO по порядку вставки в `Map` — `map.keys().next().value`). Партитура —
   это до нескольких мегабайт строки, неограниченный кеш съест память.
3. Если `statSync` бросил (файла нет) — не кешируй, дай ошибке пройти наружу как раньше.
4. Экспортируй `clearScoreCache()` и вызывай его в тестах, чтобы они не влияли друг на
   друга.

**Тест.** `server/scoreAnalyzer.test.ts`: два подряд `analyzeScoreFile` одного файла
дают одинаковый результат; после `writeFileSync` (изменения файла) результат
перечитывается. Для контроля числа чтений можно замерить, что второй вызов
существенно быстрее, но надёжнее проверить именно инвалидацию по mtime.

**Критерий приёмки.** Повторный разбор того же файла не вызывает `unzip` (проверяется
логом или тем, что тест на инвалидацию проходит), и все существующие тесты зелёные.

## D1. `fuzzyRepeatStarts`: O(n²) память и лишние вычисления

**Приоритет:** высокий — единственный квадратичный участок. **Оценка:** 1.5 часа.

**Где:** `server/adaptive-structure.ts`, функция `fuzzyRepeatStarts`.

**Что сейчас.** Функция материализует **все** пары окон:

```ts
  const pairs: Array<{ from: number; to: number; value: number }> = [];
  for (let to = window; to < means.length; to += 1) {
    for (let from = 0; from + window <= to; from += 1) {
      pairs.push({ from, to, value: similarity(means[from], means[to]) });
    }
  }
```

Три проблемы:
1. **Память O(n²).** На 1600 тактах это ~1.28 млн объектов только для того, чтобы
   посчитать один квантиль. На 4000 тактах — 8 млн объектов.
2. **Каждая пара считается полностью.** `similarity` складывает четыре компонента
   (хрома 12 измерений, бас 12, ритм 8, текстура 5) — около 40 умножений на пару,
   хотя порог отсекает 98 % пар.
3. Результат использует только **максимум по каждому `to`** — остальные значения
   нужны исключительно для квантиля.

**Что сделать.**

**Шаг 1 — квантиль без хранения пар.** Замени массив на гистограмму. Значения
`similarity` лежат в [0,1] по построению (взвешенная сумма косинусов и одного
`1 − расстояние`), поэтому гистограмма из 1000 корзин даёт квантиль с точностью 0.001,
чего для порога 0.98 более чем достаточно.

```ts
// CHANGED: квантиль считается по гистограмме, а не по массиву всех пар. Массив пар —
// это O(n²) памяти (на 1600 тактах 1.28 млн объектов) ради одного числа.
const BUCKETS = 1000;
const histogram = new Int32Array(BUCKETS);
let total = 0;
// первый проход: только заполняем гистограмму
for (let to = window; to < means.length; to += 1) {
  for (let from = 0; from + window <= to; from += 1) {
    const value = similarity(means[from], means[to]);
    histogram[Math.min(BUCKETS - 1, Math.max(0, Math.floor(value * BUCKETS)))] += 1;
    total += 1;
  }
}
// порог: наименьшее значение, выше которого лежит не больше 2 % пар
const cutoff = Math.ceil(total * 0.02);
let seen = 0;
let quantileBucket = BUCKETS - 1;
for (let bucket = BUCKETS - 1; bucket >= 0; bucket -= 1) {
  seen += histogram[bucket];
  if (seen >= cutoff) {
    quantileBucket = bucket;
    break;
  }
}
const threshold = Math.max(0.9, quantileBucket / BUCKETS);
```

Важно: итоговый `threshold` берётся как `Math.max(0.9, …)` — точно так же, как сейчас.
Нижняя граница 0.9 сохраняется, иначе изменится результат.

**Шаг 2 — второй проход только за максимумом по `to`.** Логика принятия пары остаётся
дословно той же, что сейчас (включая проверку контраста с предыдущим окном и формулу
силы). Меняется только то, что вместо массива пар мы идём по тем же индексам второй раз.

**Шаг 3 — отсечение по точной верхней оценке.** `similarity` = сумма четырёх слагаемых
с весами 0.45 / 0.2 / 0.2 / 0.15, каждое ≤ 1. Значит, посчитав только первое слагаемое
(косинус хромы, 12 умножений), мы знаем **точную верхнюю границу** всей суммы:

```
similarity ≤ 0.45 · cosChroma + 0.55
```

Если `0.45 · cosChroma + 0.55 < threshold`, пара пройти не может, и остальные 28
измерений считать не нужно. При `threshold ≥ 0.9` это требует `cosChroma ≥ 0.78`, что
отсекает подавляющее большинство пар. **Это branch-and-bound с точной границей:
результат совпадает до последнего бита.**

Реализация: добавь в `adaptive-structure.ts` вспомогательную функцию

```ts
/**
 * Точная верхняя оценка similarity по одному первому слагаемому. Остальные три
 * компонента взвешены суммарно на 0.55 и каждый не больше единицы, поэтому пара,
 * не проходящая по этой оценке, не пройдёт и по полной сумме.
 */
function similarityUpperBound(cosChroma: number): number {
  return 0.45 * cosChroma + 0.55;
}
```

и используй её в обоих проходах. Веса нельзя хардкодить в двух местах: вынеси их в
именованные константы рядом с `similarity` и используй и там, и в оценке — иначе
изменение веса в одном месте молча сломает границу.

**Ожидаемый эффект.** Память O(n²) → O(n). Время на 1600 тактах: 247 мс → ориентир
60–90 мс (порядок 3–4×). Асимптотика остаётся O(n²) — это нормально, задача не требует
менять её; требуется убрать память и лишние умножения.

**Чего делать НЕЛЬЗЯ.** Не заменяй точное сравнение на приближённое: LSH, случайные
проекции, хеширование окон, семплирование пар — всё это меняет результат и запрещено в
этой задаче. Точное отсечение по верхней границе — можно, приближённое — нет.

**Тест.** В `server/adaptive-musicality.test.ts` добавь: на синтетическом входе из 40
тактов с явным возвратом материала (первые 8 тактов повторяются с такта 24) результат
`fuzzyRepeatStarts` совпадает с эталонным набором индексов. Тест писать **до** правки,
зафиксировав текущий вывод как эталон, — тогда он и докажет неизменность.

## D2. Линейный поиск такта там, где есть ключ

**Приоритет:** высокий (это вторая причина сверхлинейного роста). **Оценка:** 1 час.

**Где:** `server/adaptive-learning.ts`, семь мест.

**Что сейчас.** Массив `measures: AdaptiveMeasureProfile[]` упорядочен и каждый элемент
несёт номер такта `measure`, но поиск по номеру идёт полным перебором:

| строка | код | сложность вызова |
|---|---|---|
| ~1879 | `measures.find((m) => m.measure === phrase.endMeasure)` | O(n) |
| ~1880 | `measures.find((m) => m.measure === next.startMeasure)` | O(n) |
| ~1901 | `measures.findIndex((m) => m.measure === candidate.anchorMeasure)` | O(n) |
| ~1958 | `measures.find((m) => m.measure === range.end)?.tickCount` | O(n) |
| ~2130 | `measures.find((m) => m.measure === end)?.tickCount` | O(n) |
| ~2178, ~2181 | `measures.find(...)` внутри двойного цикла Summarize | O(n) на итерацию |
| ~2252 | `measures.findIndex((m) => m.measure === boundary.measure)` в `insideRepeatPenalty` | O(n) |

Итого: в `buildBridgeChunks` — O(число_переходов · n); в `buildSummaryChunks` — O(p²·n),
где p — число фраз (на 1600 тактах p ≈ 200, то есть 40 000 · 1600 = 64 млн сравнений).

**Что сделать.** Номер такта — это индекс со сдвигом: `measures[i].measure === wholeStart + i`.
Заведи один раз индекс и передавай его туда, где нужен поиск:

```ts
/**
 * Индекс «номер такта → профиль». Номер такта равен wholeStart + позиция, но полагаться
 * на арифметику опасно: пьеса может начинаться не с первого такта. Карта строится один
 * раз на план и заменяет линейный поиск в Bridge, Review и Summarize.
 */
function indexMeasures(
  measures: AdaptiveMeasureProfile[],
): Map<number, AdaptiveMeasureProfile> {
  return new Map(measures.map((measure) => [measure.measure, measure]));
}
```

и вторую карту для позиции, где нужен индекс, а не объект:

```ts
function indexPositions(measures: AdaptiveMeasureProfile[]): Map<number, number> {
  return new Map(measures.map((measure, index) => [measure.measure, index]));
}
```

Строй их в `analyzeAdaptiveMusicXml` сразу после `enrichProfiles` и передавай в
`buildBridgeChunks`, `buildReviewChunks`, `buildSummaryChunks`, `insideRepeatPenalty`
дополнительным параметром. Не строй карту внутри функции, которая вызывается в цикле, —
это вернёт ту же квадратичность.

**Ожидаемый эффект.** Bridge/Review/Summarize перестают зависеть от n: суммарно
O(p² · n) → O(p²). На 1600 тактах это десятки миллисекунд.

**Тест.** Не нужен отдельный: достаточно `diff` корпусного аудита из §D0.3 (результат
обязан совпасть) и существующих 84 тестов.

## D3. DP: убрать пересчёт внутри окна через префиксные суммы

**Приоритет:** средний. **Оценка:** 1 час.

**Где:** `server/adaptive-learning.ts`, функция `optimizePhrases`.

**Что сейчас.** Внешний цикл по `end` (n итераций) × внутренний по `start`
(до `maxSpan` = 16 итераций). Внутри для каждой пары считаются три величины, каждая
своим проходом по диапазону:

```ts
      cost += crossedHardBoundaryCount(measures, start, end) * PEDAGOGY.hardBoundaryCrossPenalty;
      cost += crossedExpressiveBoundaryCount(measures, start, end) * PEDAGOGY.expressiveBoundaryCrossPenalty;
      ...
      for (let index = start; index < end - 1; index += 1) {
        if (context.navigation.discontinuityAfter[index]) {
          cost += PEDAGOGY.navigationCrossPenalty;
        }
      }
      ...
        cost += crossedSectionBoundaryCount(measures, start, end) * PEDAGOGY.sectionCrossPenalty;
```

Каждая из четырёх величин — это O(end − start) = O(maxSpan). Итог: **O(n · maxSpan²)**,
то есть на каждый такт около 4 · 16 · 16 = 1024 лишних операций.

**Что сделать.** Все четыре величины — суммы по подотрезку, значит считаются за O(1)
через префиксные суммы. Построй их один раз перед DP:

```ts
  // CHANGED: четыре величины в цене фрагмента — суммы по подотрезку. Префиксные суммы
  // превращают их из O(длина фрагмента) в O(1) и убирают квадрат по окну DP.
  const prefixHard = buildPrefix(measures, (measure) => (measure.hardBoundaryAfter ? 1 : 0));
  const prefixExpressive = buildPrefix(measures, (_, index) =>
    measures[index + 1]?.tempoTransitionLabels.length ? 1 : 0,
  );
  const prefixSection = buildPrefix(measures, (measure) =>
    measure.sectionBoundaryAfter >= 0.6 ? measure.sectionBoundaryAfter ** 2 : 0,
  );
  const prefixNavigation = buildPrefix(measures, (_, index) =>
    context.navigation.discontinuityAfter[index] ? 1 : 0,
  );
```

с общим помощником:

```ts
/** Префиксные суммы: sum(from..toExclusive) = prefix[toExclusive] − prefix[from]. */
function buildPrefix(
  measures: AdaptiveMeasureProfile[],
  value: (measure: AdaptiveMeasureProfile, index: number) => number,
): number[] {
  const prefix = [0];
  for (const [index, measure] of measures.entries()) {
    prefix.push(prefix[prefix.length - 1] + value(measure, index));
  }
  return prefix;
}
```

**Крайне важно — границы диапазонов.** Существующие функции суммируют по
`index ∈ [start, end − 1)`, то есть **не включая** последний такт фрагмента. Ровно эти
границы и надо воспроизвести: `prefix[end - 1] - prefix[start]`. Ошибка на единицу
здесь тихо изменит все разбиения. Сверься с телом `crossedHardBoundaryCount` —
цикл `for (let index = start; index < endExclusive - 1; index += 1)`.

После перехода на префиксы старые функции `crossedHardBoundaryCount`,
`crossedExpressiveBoundaryCount`, `crossedSectionBoundaryCount` удали, чтобы не
осталось двух источников правды.

**Ожидаемый эффект.** Внутренний цикл DP становится O(1) по каждому члену; для
n = 1600 это минус ~1.6 млн операций. Асимптотика O(n · maxSpan).

**Тест.** Обязательный `diff` корпусного аудита (§D0.3). Дополнительно добавь юнит-тест
на `buildPrefix`: сумма по подотрезку совпадает с наивным подсчётом на случайном
массиве из 50 чисел (сравни в цикле все пары `from < to`).

## D4. Review и Summarize: суммы секунд через префиксы, а не фильтром по всем тактам

**Приоритет:** высокий (самый заметный квадрат вне fuzzy). **Оценка:** 45 минут.

**Где:** `server/adaptive-learning.ts`, `buildReviewChunks` и `buildSummaryChunks`.

**Что сейчас.** В `buildReviewChunks`:

```ts
  const phraseSeconds = (phrase: SlicingExercise) =>
    measures
      .filter(
        (measure) =>
          measure.measure >= phrase.startMeasure &&
          measure.measure <= phrase.endMeasure,
      )
      .reduce((sum, measure) => sum + measure.estSeconds, 0);
```

Это O(n) на одну фразу. И вызывается она внутри цикла по фразам ещё и повторно для всей
накопленной группы:

```ts
    const currentSeconds = current.reduce(
      (sum, item) => sum + phraseSeconds(item),
      0,
    );
```

Итог: O(p² · n) на построение Review. На 1600 тактах (p ≈ 200) это порядка 64 млн
операций — и это при том, что все нужные суммы считаются одним проходом.

В `buildSummaryChunks` та же картина: префикс по фразам там уже есть (`prefix`), но
внутри двойного цикла по `first`/`second` делается `measures.find(...)` — см. D2.

**Что сделать.**

1. Построй **один** массив префиксных сумм секунд по индексу такта:

```ts
  // CHANGED: суммы секунд по диапазону считаются префиксом. Фильтр по всем тактам на
  // каждую фразу давал O(число_фраз² · число_тактов) там, где достаточно одного прохода.
  const prefixSeconds = buildPrefix(measures, (measure) => measure.estSeconds);
  const positionOf = indexPositions(measures); // из D2
  const rangeSeconds = (startMeasure: number, endMeasure: number) => {
    const from = positionOf.get(startMeasure);
    const to = positionOf.get(endMeasure);
    if (from === undefined || to === undefined) return 0;
    return prefixSeconds[to + 1] - prefixSeconds[from];
  };
```

2. Замени `phraseSeconds(phrase)` на `rangeSeconds(phrase.startMeasure, phrase.endMeasure)`.
3. Накопленную сумму группы веди инкрементально: прибавляй секунды новой фразы к
   переменной, а не пересчитывай `current.reduce(...)` целиком. При закрытии группы
   сбрасывай накопитель в ноль.
4. В `buildSummaryChunks` замени `measures.find(...)` на карту из D2.

**Ожидаемый эффект.** Review: O(p² · n) → O(p). Summarize: O(p² · n) → O(p²).

**Тест.** `diff` корпусного аудита. Плюс добавь в `server/adaptive-learning.test.ts`
проверку на партитуре из 24 тактов (такая уже есть в тестах — используй её): диапазоны
Review не изменились по сравнению с ожидаемыми в существующем тесте.

## D5. Разбор такта: один проход вместо восьми и кеш скомпилированных регексов

**Приоритет:** высокий (это те самые ≈41 мс из 81.7 на Clocks). **Оценка:** 3 часа.
**Осторожно:** самая рискованная задача раздела — делай её последней.

**Где:** `server/adaptive-learning.ts`, функция `profileMeasure` и помощники
`extractElements`, `extractTagAttributes`, `tagValue`, `attributeValue`,
`extractScopedNotes`, `extractVoiceStreams`, `countTicks`, `hasTieAcrossMeasure`.

**Что сейчас — две независимые проблемы.**

**(а) Регулярные выражения компилируются на каждый вызов.**

```ts
function extractElements(xml: string, tag: string) {
  const pattern = new RegExp(`<${tag}(?=\\s|>)([^>]*)>([\\s\\S]*?)<\\/${tag}>`, "gi");
```

```ts
function tagValue(xml: string, tag: string): string {
  const match = xml.match(new RegExp(`<${tag}(?=\\s|>)[^>]*>([\\s\\S]*?)<\\/${tag}>`, "i"));
```

`tagValue` вызывается для каждой ноты по нескольким тегам (`step`, `octave`, `alter`,
`staff`, `voice`, `type`, `duration`) — это тысячи компиляций регулярного выражения на
партитуру. Компиляция дороже самого поиска на короткой строке.

**Что сделать:** кеш по строке тега.

```ts
// CHANGED: шаблон зависит только от имени тега, а компиляция дороже самого поиска на
// короткой строке такта. Раньше `new RegExp` вызывался тысячи раз на партитуру.
const tagValuePatterns = new Map<string, RegExp>();

function tagValuePattern(tag: string): RegExp {
  const cached = tagValuePatterns.get(tag);
  if (cached) return cached;
  const pattern = new RegExp(`<${tag}(?=\\s|>)[^>]*>([\\s\\S]*?)<\\/${tag}>`, "i");
  tagValuePatterns.set(tag, pattern);
  return pattern;
}
```

Сделай то же для `extractElements`, `extractTagAttributes`, `attributeValue` — и
**обязательно для их копий в `server/adaptive-notes.ts`** (там те же четыре функции).

**Ловушка:** у глобальных регексов (`g`/`gi`) есть состояние `lastIndex`. Кешировать их
можно **только** при использовании через `str.matchAll(pattern)` — этот метод клонирует
регекс внутри себя. Если где-то используется `pattern.exec` в цикле или
`pattern.test`, кешированный глобальный регекс сломает логику. Проверь каждое место
перед кешированием; для `test` кешируй регекс **без** флага `g`.

**(б) Тело такта сканируется примерно восемь раз.**
`profileMeasure` получает строку и извлекает из неё ноты заново для каждой задачи:
`extractElements(body, "note")`, затем фильтры `sounding`/`attacks`, отдельно
`extractScopedNotes(body)`, отдельно `extractVoiceStreams(body)`, отдельно
`countTicks(body)`, отдельно `hasTieAcrossMeasure(body)`, отдельно `extractElements(body, "lyric")`.
При этом в проекте **уже есть** структурная модель: `extractMeasureNotes` из
`server/adaptive-notes.ts` возвращает `MeasureNotes` с событиями, у которых разобраны
`onset`, `duration`, `midi`, `staff`, `voice`, `tieStart/tieStop`, артикуляции,
орнаменты, лиги.

**Что сделать:** передавай `profileMeasure` уже разобранный такт и считай по нему то,
что сейчас считается регексами по строке. Порядок работы — строго по шагам, с
проверкой после каждого:

1. Измени сигнатуру: `profileMeasure(body, ordinal, measureQuarterBeats, divisions, notes: MeasureNotes)`.
   В `analyzeAdaptiveMusicXml` модель уже строится (`buildMusicalContext` → `extractMeasureNotes`),
   но **сейчас она строится после** `raw.map(profileMeasure)`. Поменяй порядок: сначала
   `extractMeasureNotes`, потом `profileMeasure` с готовой моделью.
2. Переведи на модель по одному полю за раз, каждый раз прогоняя `bun test` и `diff`
   аудита: `noteCount`, `chordCount`, `attackCount`, `maxChordSize`,
   `firstPitchByStaff`/`lastPitchByStaff`, `maxLeap`, `voices`, `fastestNote`,
   `ornamentCount`, `articulationRatio`, `gestureTechniques`, `tiedIntoNext`,
   `tickCount`.
3. `tickCount` — особый случай: это значение уходит в Piano Marvel (`end_tick` в
   `server-method-162`). Формула снята с живых данных: различные позиции начала событий
   (ноты и паузы), `<chord>` — та же позиция, `<grace>` не считается. В модели это
   `new Set(events.filter(e => !e.grace).map(e => e.onset)).size` — но проверь на
   тестах `adaptive-learning.test.ts`, там есть кейсы на затакт и на backup/forward.
4. Что **не** переводится на модель: `direction`-элементы (tempo/dynamic/pedal/metronome),
   `barline`, `rehearsal`, `print`, `lyric`. Они не ноты, их разбор остаётся строковым.
5. Только когда все поля переведены и `diff` пуст — удали ставшие ненужными
   `extractVoiceStreams`, `countTicks`, `hasTieAcrossMeasure`, `extractScopedNotes`
   из `adaptive-learning.ts`.

**Ожидаемый эффект.** Стадия разбора ≈41 мс на Clocks → ориентир 10–15 мс; на 1600
тактах вклад падает пропорционально. Плюс исчезает дублирование логики парсинга между
двумя файлами.

**Если задача идёт тяжело — останови её и зафиксируй в отчёте.** Пункт (а), кеш
регексов, самостоятельный и безопасный: он даёт заметную часть выигрыша и его можно
сдать отдельно.

## D6. Выборки из SQLite: не читать таблицу, чтобы вернуть одну строку

**Приоритет:** средний. **Оценка:** 1 час.

**Где:** `server/cache.ts`.

**Измерено.** 100 чтений `getLearningStatus(7)` на таблице из N записей:

| N записей | время 100 чтений | на одно чтение |
|---|---|---|
| 50 | 1.3 мс | 0.013 мс |
| 500 | 8.0 мс | 0.080 мс |
| 2000 | 34.0 мс | 0.340 мс |

Время на одно чтение растёт **линейно по размеру таблицы** — при том что `piece_id`
объявлен `INTEGER PRIMARY KEY`, то есть поиск обязан быть O(log N).

**Причина.** `getLearningStatus` делегирует в `getLearningStatuses([pieceId])`, а тот
читает **всю таблицу** и фильтрует в JavaScript:

```ts
      .all(LEARNING_ALGORITHM_VERSION)
      .filter((row) => !allowed || allowed.has(row.piece_id))
```

**Что сделать.**

1. Отдельный путь для одной записи — параметризованный поиск по ключу:

```ts
  getLearningStatus(pieceId: number): CachedLearningStatus | undefined {
    // CHANGED: поиск по первичному ключу вместо чтения всей таблицы с фильтром в JS.
    const row = this.db
      .query<StatusRow, [number, string]>(
        `SELECT piece_id, payload, checked_at
           FROM learning_status_cache
          WHERE piece_id = ? AND algorithm_version = ?`,
      )
      .get(pieceId, LEARNING_ALGORITHM_VERSION);
    if (!row) return undefined;
    const status = parseJson<LearningStatus>(row.payload)[0];
    return status ? { status, checkedAt: row.checked_at } : undefined;
  }
```

2. Для множественного случая передавай список в сам SQL, а не фильтруй после:

```ts
  getLearningStatuses(pieceIds?: number[]): CachedLearningStatus[] {
    // Плейсхолдеры строятся по длине списка — значения по-прежнему параметризованы,
    // никакой склейки значений в текст запроса.
    const placeholders = pieceIds?.length
      ? ` AND piece_id IN (${pieceIds.map(() => "?").join(",")})`
      : "";
    ...
  }
```

**Важно:** если `pieceIds` пустой массив — это «ничего не запрашивали», верни `[]` без
запроса. И не строй условие для `undefined` (запрос всех) — там условия быть не должно.

3. **Кешируй подготовленные выражения.** Сейчас `this.db.prepare(...)` вызывается на
   каждый вызов метода — то есть SQL компилируется заново при каждой записи статуса и
   каждом сохранении пьесы. Держи их полями класса, создавая лениво:

```ts
  /** Подготовленные выражения переиспользуются: SQL компилируется один раз. */
  private statements = new Map<string, ReturnType<Database["prepare"]>>();

  private statement(sql: string) {
    const cached = this.statements.get(sql);
    if (cached) return cached;
    const prepared = this.db.prepare(sql);
    this.statements.set(sql, prepared);
    return prepared;
  }
```

и замени `this.db.prepare(...)` на `this.statement(...)` в `putPiece`,
`putLearningStatus`, `putScoreSource`, `replaceCatalog`, `saveSession`.

4. **Обёртка транзакции для пакетной записи.** `replaceCatalog` делает `DELETE` плюс N
   вставок отдельными операциями:

```ts
    this.db.run("DELETE FROM cached_pieces");
    const insert = this.db.prepare(...);
    for (const piece of items) insert.run(piece.id, JSON.stringify(piece));
```

   Оберни в транзакцию — на каталоге из сотен пьес это разница в разы:

```ts
    // CHANGED: одна транзакция вместо N неявных. При каталоге в сотни пьес это
    // сотни отдельных фиксаций вместо одной.
    this.db.transaction(() => {
      /* DELETE + цикл вставок */
    })();
```

**Тест.** В `server/cache.test.ts` добавь: записать 200 статусов, прочитать один —
результат правильный; прочитать список из трёх id — вернулись ровно три, в том числе
после записи статуса с другой `algorithm_version` (он не должен попасть в выборку).

**Критерий приёмки.** Время одного чтения `getLearningStatus` не растёт при
увеличении таблицы с 50 до 2000 записей (замер тем же способом, что в §D0.2).

## D7. `noveltyCurve`: инкрементальные блоки

**Приоритет:** низкий (измерено: 19 мс на 1600 тактов). **Оценка:** 1 час.

**Где:** `server/adaptive-structure.ts`, функция `noveltyCurve`.

**Что сейчас.** Для каждого стыка считаются три блочных сходства:

```ts
    raw[index] = clamp01(
      (blockSimilarity(before, before) + blockSimilarity(after, after)) / 2 -
        blockSimilarity(before, after),
    );
```

`blockSimilarity(a, b)` — двойной цикл, то есть O(w²) вызовов `similarity`. Итого
O(n · w² · d), где w = размер окна (4…8), d ≈ 40 измерений.

Соседние стыки используют почти одинаковые блоки: при переходе от `i` к `i+1` из блока
«до» уходит один такт и приходит один. Значит самоподобие блока обновляется за O(w), а
не пересчитывается за O(w²).

**Что сделать (только если остальные задачи D закрыты).** Веди сумму попарных сходств
внутри блока как накопитель: при добавлении такта прибавь его сходство с каждым из уже
входящих (O(w)), при удалении — вычти. Взаимное сходство блоков «до»/«после» так не
упрощается, поэтому останется O(w²) — общая сложность станет O(n · w² · d) → O(n · w · d)
для двух слагаемых из трёх.

**Честная оценка выгоды:** примерно −40 % от 19 мс на 1600 тактах, то есть около 8 мс.
Браться стоит только если D1–D6 уже сделаны и хочется довести стадию до конца.

**Тест.** `diff` корпусного аудита — обязательно: ошибка в накопителе даст другие швы
формы.

## D8. Поправка к задаче B3: тревога была ложной

**Что делать:** понизить приоритет B3 и **не переписывать** `maximalRepeats` на
суффиксные структуры.

**Почему.** В части B задача B3 описана как защита от квадратичного роста в
`maximalRepeats`. Замеры этого не подтверждают: даже в худшем случае (1600 полностью
одинаковых тактов, то есть максимально большие группы одинаковых отпечатков) функция
занимает **18 мс**, а на реальной партитуре — **0.3 мс**. Существующие ограничители
работают: расширение прерывается при перекрытии (`first + length >= second`), а
проверка `minimalPeriod` отбрасывает остинатные окна целиком.

**Что сделать вместо этого.**
1. В части B пометь B3 как «низкий приоритет, подтверждено замерами: 18 мс в худшем
   случае» и оставь только один пункт из неё — **пропуск групп больше 200 позиций** как
   страховку от партитуры на десятки тысяч тактов. Остальное не делай.
2. Переписывание на суффиксный массив с LCP (теоретически O(n log n) вместо
   O(Σ|группа|² · длина)) **не требуется**: выигрыш измеряется единицами миллисекунд, а
   риск изменить музыкальный результат высок.

Эта поправка — часть задачи D0: сначала измерь, потом решай. Если твои замеры на другой
машине покажут иное, приложи их к отчёту.
