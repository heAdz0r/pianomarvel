# PRD: производительность, конкурентная безопасность и нагрузка UI

**Дата:** 2026-08-16  
**Статус:** Approved for implementation — пользователь попросил сразу приступить  
**Область:** `src/App.vue`, `src/components/PiecesMovement.vue`, `src/motion.ts`, стили и связанные unit-тесты

## 1. Проблема

Локальный интерфейс функционален, но каталог авторизованного пользователя создаёт около 2100 DOM-узлов, а production build содержит основной JS 359.88 kB (127.43 kB gzip), CSS 208.07 kB (36.69 kB gzip) и отложенный OpenSheetMusicDisplay 1,275.62 kB (337.06 kB gzip). На странице работают постоянные декоративные анимации и несколько глобальных наблюдателей DOM.

Есть подтверждённые конкурентные дефекты:

1. `setInterval(async ...)` проверки логина допускает пересечение запросов и позднюю запись устаревшего статуса.
2. Массовое создание Learn Mode запускает фоновый watcher и отдельный `waitForFinalLearningJob` для каждой одной и той же job, удваивая long-poll запросы.
3. Повторные scan/catalog-запросы не имеют общего latest-wins guard; старый ответ может перезаписать новый.

## 2. Цели

- Исключить пересекающийся polling и stale-response overwrite.
- Оставить ровно один long-poll поток на одну learning job.
- Сократить критический JS-путь за счёт ленивой загрузки каталога и нотного viewer.
- Остановить кадровые циклы, когда визуально нечего обновлять или вкладка скрыта.
- Снизить layout/paint стоимость секций ниже первого экрана без изменения UX.
- Сохранить `prefers-reduced-motion`, доступность и существующие переходы.

## 3. Не-цели

- Не менять музыкальные алгоритмы, Piano Marvel API и формат MXL.
- Не заменять Vue/TanStack/OSMD.
- Не удалять фирменные анимации целиком.
- Не оптимизировать внешнюю скорость Piano Marvel, которая не контролируется приложением.

## 4. User stories

1. Как пользователь, я не должен видеть возврат устаревшего статуса после завершения входа или нового сканирования.
2. Как пользователь каталога, я хочу быстрее получить интерактивный первый экран, пока тяжёлая библиотека загружается только после подтверждения входа.
3. Как пользователь ноутбука, я не хочу постоянную нагрузку CPU/GPU от неподвижного курсора и невидимой маркизы.
4. Как оператор массового обновления, я хочу один поток статуса на задачу без дублирующих запросов.

## 5. Функциональные требования

| ID | Требование | Acceptance criteria |
|---|---|---|
| P1 | Latest-wins для scan/catalog | предыдущий запрос abort; его ответ не изменяет state |
| P2 | Последовательный login polling | следующий запрос стартует только после завершения предыдущего; complete/unmount инвалидирует старый run |
| P3 | Один watcher на learning job | bulk-flow не вызывает одновременно background watcher и final waiter |
| P4 | Ленивые чанки | каталог не входит в initial JS; viewer загружается только при открытии аппликатуры |
| P5 | Анимации по необходимости | cursor RAF останавливается в покое/hidden; marquee паузится вне viewport |
| P6 | Дешёвый DOM monitoring | DOM-мутации обрабатываются батчем не чаще одного раза за frame |
| P7 | Below-fold rendering | библиотека использует `content-visibility: auto` с безопасным intrinsic size |

## 6. Нефункциональные критерии

- Все существующие тесты проходят.
- Добавлены unit-тесты latest-request guard.
- Production build успешен; initial JS gzip должен уменьшиться относительно 127.43 kB.
- Нет новых непрерывных timer/RAF циклов.
- При `prefers-reduced-motion: reduce` декоративные движения не запускаются.

## 7. Риски и откат

- Lazy chunk может кратко показать пустую секцию: Vue async component сохраняет декларативный mount, а каталог и так появляется только после проверки входа.
- `content-visibility` может изменить оценочную высоту: задан intrinsic size, поведение проверяется в Chromium.
- Abort клиента не гарантирует отмену уже начатой серверной операции; latest-wins всё равно не позволяет старому ответу испортить UI.

Откат выполняется независимо по четырём поверхностям: async imports, latest-request guard, learning watcher mode, motion/CSS.

## 8. План проверки

1. Unit: latest-request abort/current semantics; все существующие Bun tests.
2. Static: `vue-tsc --noEmit`, `vite build`, `git diff --check`.
3. Browser: initial DOM, ленивые чанки, видимые/бесконечные анимации, переключение источника и каталог.
4. Сравнить размеры build до/после и зафиксировать результат в perf report.

## 9. Результат реализации (2026-08-16)

Статус P1: реализован. Входной JavaScript уменьшен с 127,43 до 56,06 kB gzip (-56,0%), входной CSS — с 36,69 до 15,06 kB gzip (-58,9%). Каталог, его CSS и нотный рендерер вынесены в ленивые чанки.

- Опрос статуса входа переведён с пересекающегося `setInterval` на последовательный `setTimeout` с защитой поколения.
- Сканирование папки и обновление каталога используют latest-request-wins: предыдущий запрос отменяется, устаревший ответ не меняет состояние.
- Удалено дублирование long-poll наблюдателей при массовом обучении.
- Наблюдатели DOM объединяют мутации в один `requestAnimationFrame`; offscreen-маркиза ставится на паузу.
- Для длинного каталога включён `content-visibility: auto`, а у reveal-анимации удалены дорогой blur и постоянный `will-change`.

Production-сборка и новые unit-тесты проходят. Полный набор тестов имеет 2 сбоя в параллельно изменённом `server/adaptive-learning.test.ts`; typecheck также показывает две существующие/параллельные проблемы вне области этой оптимизации. Они перечислены в отчёте проверки и не замаскированы.
