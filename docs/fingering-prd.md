# PRD: Автоматическая аппликатура MusicXML — «Fingering Compiler»

Статус: **реализовано с явно перечисленными границами** (фазы P0–P7.11).
Документ описывает функцию «подобрать аппликатуру, если её нет в партитуре»,
прямой вход из строки таблицы, визуальный нотный стан, пересборку и открытие
производного MXL. Замеры на реальном корпусе — в §2.3, структура локальной
библиотеки — в §7.4, причины ошибок первоначальной реализации — в §13.

Не сделано из описанного: подсветка «все ноты, где сработало правило» (§9.3) и
выбор размера руки в UI. Автотест обновления Piano Marvel проверяет точный
локальный attachment/path, но не мутирует живую внешнюю композицию без явного
действия авторизованного пользователя. Вкладка больше не рисует собственный упрощённый стан:
`FingeringScore.vue` передаёт полный `previewXml` в OpenSheetMusicDisplay
(OSMD), который гравирует исходную MusicXML-нотацию и добавленные цифры.
MuseScore остаётся финальной проверкой всего документа и печатной вёрстки, но
выбранный такт в UI теперь является настоящим MusicXML-рендером, а не
реконструкцией по сокращённому массиву нот.

Правило номер один, унаследованное от [Adaptive PRD](adaptive-learning-prd.md):
**никакого хардкода по названию пьесы, тональности или номеру такта**. Каждая
константа либо выведена из партитуры, либо живёт в `DEFAULT_WEIGHTS`,
`FINGERING_SEARCH` / `PEDAGOGY` со ссылкой на источник и тестом
чувствительности.

Правило номер два, специфичное для этой функции: **оригинал неприкосновенен**.
Аппликатура пишется только в новый файл; исходный `.mxl` не открывается на
запись ни при каких условиях.

## 1. Проблема

`server/scoreAnalyzer.ts` умеет читать метаданные и оценивать сложность, но
про аппликатуру не знает ничего: в коде проекта нет ни одного упоминания
`<fingering>`. Между тем большинство партитур, приходящих с MuseScore
(`server/musescore.ts`) и с диска, аппликатуры не содержат вообще, а Piano
Marvel её не генерирует — он отображает то, что есть в MusicXML.

Для ученика это ключевая потеря: без аппликатуры Learn Mode (в том числе
Adaptive-нарезка Phrase → Bridge → Review → Summarize → Whole) отрабатывает
структуру музыки, но не отрабатывает **моторный план**. Аппликатура — это
единственный слой нотации, который напрямую кодирует движение руки; выбранная
наугад, она закрепляет неверную моторику, и переучивание стоит дороже, чем
первичное разучивание (Chaffin & Imreh о «моторных зацепках» — см. §15).

Отсюда две задачи:

1. **Определить**, есть ли в партитуре аппликатура и насколько она полна.
2. Если её нет — **вывести** оптимальную аппликатуру из музыки и эргономики
   руки и сохранить её в **новый** `.mxl`, не трогая оригинал.

### 1.1 Почему это трудно

Задача не сводится к «поставить удобный палец на каждую ноту»:

- Стоимость **не локальна**: выбор пальца на ноте *n* меняет цену перехода
  *n → n+1* и *n+1 → n+2* (правила смены позиции у Parncutt смотрят на тройки).
- Пространство решений **экспоненциально**: 5^N для одноголосия, гораздо больше
  для аккордов (нужно назначать множества пальцев).
- «Правильного ответа» нет даже у людей: согласие между пианистами на корпусе
  PIG — **≈71 %** (Nakamura, Saito & Yoshii, 2020). Это эмпирическая
  калибровка разброса разметки, а не универсальный математический потолок для
  любого произведения, редактора и протокола сравнения.
- Педагогическая норма (гаммы, арпеджио, альбертиев бас) во многих местах
  **сильнее** чистой эргономики: играть гамму «удобным» способом с большим
  пальцем на чёрной клавише формально дешевле по стоимости перехода, но
  противоречит всей школе (Clementi, Czerny, Hanon, ABRSM/RCM).

Следовательно, нужен слоистый алгоритм. Физическая допустимость эргономической
модели всегда является hard-gate. Вне распознанного паттерна её стоимость
ранжирует варианты. Внутри канонической гаммы, арпеджио, пятипальцевой ячейки
или точного остинато крупные педагогические приоры намеренно доминируют
ранжирование; эргономика там остаётся проверкой выполнимости, сравнением
педагогически равных кандидатов и отдельной оценкой нагрузки.

## 2. Цель и критерии успеха

**Цель.** При загрузке композиции в таблицу пользователь может одним чекбоксом
получить партитуру с проставленной аппликатурой обеих рук, сохранённую как
новый `.mxl` рядом с оригиналом, и загрузить в Piano Marvel именно её.

### 2.1 Функциональные критерии

| # | Критерий | Проверка |
|---|---|---|
| F1 | Детекция: для любой партитуры известно `hasFingering`, `coverage` (доля нот с аппликатурой), `annotatedNotes/totalNotes` | unit-тест на фикстурах с/без аппликатуры |
| F2 | Если `coverage ≥ 0.6` — генерация **не запускается**, используется оригинал | тест + сообщение в UI |
| F3 | Генерация покрывает звучащие ноты поддерживаемого фортепианного слоя; продолжения tie наследуют палец, а физически невозможные вертикали и ноты вне первых двух нотоносцев/партий пропускаются с точным `warning` | инварианты и degradation-тесты |
| F4 | Новый файл — валидный `.mxl` (mimetype первым, без сжатия; `META-INF/container.xml`; та же партитура + `<fingering>`) | round-trip: распаковать, распарсить, сравнить число нот |
| F5 | Оригинал побайтово не изменён | хеш до/после |
| F6 | Идемпотентность: повторный запуск на уже сгенерированном файле не создаёт дублей `<fingering>` | тест |
| F8 | На композицию приходится ровно **два целевых файла**: ресурсный `fingered/<имя>.mxl` и совместимый с загрузчиком `fingered/piano-marvel/<имя>.mxl`; пересборка перезаписывает их | тест на содержимое папки после двух прогонов |
| F7 | Детерминизм: один вход → один выход (нет `Math.random`, стабильные тай-брейки) | тест на два прогона |
| F9 | Анализ и сборка возвращают полный `previewXml` с планом, а UI гравирует выбранный такт через OSMD без повторного чтения файла с диска | API-тест + browser smoke: в контейнере появляется OSMD SVG |
| F10 | Кнопка «Ноты и аппликатура» является toggle; такт выбирается слайдером, кнопками, прямым номером и клавишами ←/→/Home/End | component/browser-тест состояний и клавиатуры |
| F11 | Обновление существующей композиции Piano Marvel принимает явный `original`/`fingered`, проверяет фактически отправленный path и никогда не меняет канонический `score_sources` на производный файл | endpoint + exact-attachment test; live-мутация остаётся ручным действием авторизованного пользователя |
| F12 | Нотная головка в OSMD доступна мышью и клавиатурой; hover/focus показывает высоту, длительность, палец, руку/стан, voice и контекст tie/tuplet/chord без изменения MusicXML | parser/mapping/component tests + ручная визуальная проверка |

### 2.2 Музыкальные критерии

| # | Критерий | Порог |
|---|---|---|
| M1 | Диатоническая гамма ≥ 8 нот подряд получает аппликатуру школы (большой палец только на белой, группы 3+4) | gold-таблица всех 12 мажорных гамм обеих рук; для натурального, гармонического и мелодического минора — инварианты и интеграционные примеры без таблицы «по памяти» |
| M2 | Распознанное трезвучное арпеджио ≥ 6 нот получает канонический групповой рисунок 1-2-3(-5) / 5-3(4)-2-1 | gold-тест C-dur обеих рук + проверка структуры трезвучия/септаккорда; расширение gold-корпуса по тональностям остаётся задачей корпуса |
| M3 | Большой палец на чёрной клавише в гаммообразном пассаже | ≤ 1 % нот |
| M4 | 4-й палец на чёрной при 3-м на белой (правило 9) | ≤ 3 % переходов |
| M5 | Нет физически невозможных **одновременных** растяжений и связных переходов: внутри аккорда и при пальцевом легато интервал ≤ `MaxPrac`; нелегатный перенос руки не является растяжением | 0 напечатанных нарушений; невозможная вертикаль подавляется с `warning` |
| M6 | Под лигой (`<slur>`) один и тот же палец на разных высотах | 0 автоматически созданных случаев |
| M7 | Стоимость и совпадение с автором измеряются воспроизводимым read-only bench | каждая строка содержит три раздельные метрики: `costPerNote` (objective), `ergonomicCostPerNote` и `pedagogyAdjustmentPerNote`; порог не объявляется acceptance gate, пока общий корпус не хранится вместе с проектом |
| M8 | Быстрая учебная ячейка на пяти высотах сохраняет одну позицию руки | gold-тест зеркальных RH/LH beam-ячеек, транспозиции и независимости префикса от следующего такта |
| M9 | Межголосовой перехват не создаёт ложное пальцевое legato в полифонии без педали | pedal timeline + role-aware штраф + gold-тест двухголосной инвенции без педали; полный корпус без регрессии |
| M10 | Невозможная крайняя нота может перейти другой руке только при единственном строгом непересекающемся разбиении; неоднозначная, связная или авторски размеченная вертикаль не перераспределяется | симметричные RH→LH/LH→RH tests, ambiguity/legato/authored guards; 0 warnings на корпусе |

Все счётчики отчёта — **события**, а не очки правил: «смена позиции» это одна
смена, а не 2 очка полной смены; «большой на чёрной» — одна нота, а не 5 очков
правила 10. Очки остаются внутри модели и видны только в трассировке.

### 2.3 Измерено на реальном корпусе

Read-only прогон по канонической библиотеке
`~/Downloads/musescore_sheets` (без производных `fingered/`), режим полной
пересборки, ревизия после корпусных исправлений:

| показатель | результат |
|---|---:|
| уникальных партитур | 21 |
| поддерживаемых атак | 23 375 |
| напечатанных цифр на атаках | 23 375 (**100 %**) |
| консервативно подавленных атак | 0 |
| предупреждений | 0 |
| MXL-контейнеров, прошедших чтение/ZIP/XML-проверку | 21/21 |

Lumière теперь проходит 1 492/1 492. В такте 44 единственная на всём корпусе
консервативная cross-hand передача переносит крайнюю C♯4 (`midi 61`,
`noteIndex 881`) с печатного верхнего стана из RH в LH. Других межручных
переносов корпус не потребовал. Продолжения tie не считаются новыми атаками:
служебный список `plan.suppressed` нельзя смешивать с подавленными атаками bench.

Контрольный выброс стоимости Gymnopédie также снят: 455/455 атак, 0 warnings,
`costPerNote = 9.382`, из них эргономика `9.651` и педагогическая
поправка `−0.268`. `costPerNote` теперь действительно равен полной objective
cost, а не дублирует эргономическую колонку. Для разработчика это корректная
целевая функция, но для ученика отрицательное значение не является «ценой
ноты». Поэтому UI показывает основной цифрой `ergonomicCostPerNote`, рядом
компактно — педагогическую скидку/надбавку; objective остаётся внутренней
диагностикой и bench-метрикой.

| переносимый эталон | источник цифр | совпало |
|---|---|---:|
| Hanon, упражнения 1–30 | `<fingering>` | **789/1047 (75,36 %)** |
| Piano Major Scales | плотные numeric lyrics | **861/870 (98,97 %)** |
| Love Story | `<fingering>` | 58/103 (56,31 %) |
| Bad Habits easy | `<fingering>` | 8/12 (66,67 %, малая выборка) |

Для сопоставления с человеческой аппликатурой основной показатель — агрегат
только по `<technical><fingering>` в Hanon, Love Story и Bad Habits:
**855/1 162 = 73,6 %**. Numeric lyrics из учебной таблицы гамм полезны как
отдельный педагогический gold, но не смешиваются с этой цифрой.

Независимый аудит обнаружил методологическую ловушку: прежний рекурсивный bench
заходил в `fingered/` и мог сравнить модель с её собственным выводом. На одном
Clocks это добавляло 2 571 совпадение из 2 571 и поднимало смешанную метрику до
93,1 %. Без self-generated файла она составляла 84,4 %, а честная техническая
человеческая разметка — указанные **73,6 %**. Поэтому каталоги с basename
`fingered` являются безусловным исключением обхода; строка отчёта должна
помечать тип эталона, а агрегатор — не смешивать `technical`,
`numeric-lyrics` и отсутствующий эталон.

До пятипальцевого детектора Hanon давал 535/1047 (51,10 %): эргономическая
цель систематически сжимала пальцы `3→2`, `4→3`, `2→1` и противоречила цели
упражнения. После детектора худшие учебные ячейки исправились с 1/16 и 0/16 до
16/16 и 15/16 без проверки имени файла. Значение ≈71 % из Nakamura et al.
(2020) остаётся только ориентиром межэкспертного разброса на другом корпусе;
на него нельзя нормировать конкретное издание Hanon.

Отдельная проверка Clocks: новый план печатает 2 571/2 571 атак с нулём
предупреждений. Первые повторяющиеся формы стабильны:
E♭–B♭–G `5-2-1`, D♭–B♭–F `5-3-1`, C–A♭–F `5-2-1`.

**Чего мы НЕ обещаем.** Совпадения с конкретным изданием (Henle, Peters,
редакция Корто): у редакторов расходятся фразировка, артикуляция и моторные
предпочтения. Метрика проекта — «музыкально защитимая аппликатура», а не «та
же, что у редактора».

## 3. Инварианты

1. **Оригинал не перезаписывается.** Запись только в `fingered/` внутри папки
   партитуры.
2. **Две целевые версии на композицию.** Ресурсная сохраняет привязку каждой
   цифры к ноте, PM-версия учитывает ограничения импортера. Ни `.rebuilt.mxl`,
   ни версий с датой: пересборка перезаписывает те же файлы, а сборка из уже
   сгенерированного `.mxl` кладёт результат на его же место, а не в
   `fingered/fingered/`. История версий не нужна — оригинал цел, генерация
   детерминирована и повторяется за десятки миллисекунд (§7.3).
3. **Открывать можно только партитуры.** Ручка `/api/fingering/open` принимает
   существующий `.mxl`/`.musicxml`/`.xml` и ничего больше: локальный инструмент
   не должен превращаться в «запусти что угодно» (§8.5).
4. **Никакого хардкода по произведению.** Ни имён файлов, ни тональностей, ни
   «если Гимнопедия, то…».
5. **Явная деградация.** Ноты вне первых двух партий/нотоносцев, вертикаль
   шире пяти одновременных нот в одной руке или физически невозможная форма,
   отсутствие высот — неподдержанный фрагмент не получает непроверенных цифр,
   факт попадает в `warnings`, остальная партитура обрабатывается.
6. **Всё, что нельзя вывести из партитуры, — константа с источником.** Размер
   руки, веса правил, пороги паттернов лежат в одном блоке и покрыты тестом
   чувствительности.
7. **Не ломаем существующий pipeline.** При выключенном чекбоксе поведение
   `/api/scan` и `/api/upload` идентично сегодняшнему.

## 4. Модель данных

Используем отдельный `server/fingering-score.ts`: он повторяет временную
семантику MusicXML (`divisions`, `backup`/`forward`, аккорды, grace, tie,
slur, голоса), но дополнительно сохраняет порядковый индекс и смещения каждого
`<note>`. Без них нельзя точечно вставить цифры, не сериализуя партитуру заново.
Поддерживается `score-partwise`; `score-timewise` явно отклоняется с
предупреждением.

```ts
// server/fingering.ts
export type Finger = 1 | 2 | 3 | 4 | 5;
export type Hand = "L" | "R";

/** Одна звучащая нота, поставленная в очередь на назначение пальца. */
interface FingerNote {
  index: number;       // порядковый номер <note> — ключ для точечной записи
  measureIndex: number;
  measureNumber: string;
  onset: number;       // абсолютное время в четвертях от начала пьесы
  measureOnset: number;
  duration: number;
  midi: number;
  step: string;        // исходное написание: D♯ не превращается в E♭ в UI
  alter: number;
  octave: number;
  keyFifths?: number;  // действующий ключ именно в этой точке
  keyMode?: "major" | "minor";
  black: boolean;      // pitchClass ∈ {1,3,6,8,10}
  hand: Hand;
  voice: string;
  staff: string;
  tiedFrom: boolean;   // продолжение лиги-tie: палец наследуется
  slurStarts: string[];
  slurStops: string[];
  beamBegin: boolean;
  beamEnd: boolean;
  hardBreakBefore: boolean;
  articulations: string[];
  grace: boolean;
}

/** Один onset руки: сначала строгий аккорд, при физическом отказе — слои voice. */
interface HandEvent {
  onset: number;
  notes: FingerNote[]; // отсортированы по высоте
  gapBefore: number;   // пауза перед событием в четвертях
  slurredBefore: boolean;
  beamBegin: boolean;
  beamEnd: boolean;
}
```

Выход движка:

```ts
export interface FingeringPlan {
  /** Ключ — порядковый номер элемента `<note>` в документе. */
  assignments: Map<number, Finger>;
  /** Рука, реально выбранная разделителем голосов; используется для placement. */
  hands: Map<number, Hand>;
  /**
   * Палец известен, но печатать его нельзя: продолжения лиги (звук не берётся
   * заново) и «лишние» ноты сверхшироких аккордов. Без этого множества файл
   * получает цифры там, где их нет ни в одном издании.
   */
  suppressed: Set<number>;
  report: FingeringReport;   // покрытие, карта тактов, паттерны, статистика
  trace: FingeringTrace[];   // по записи на ноту, собирается по запросу
}
```

## 5. Детекция: есть ли аппликатура

```ts
export interface FingeringCoverage {
  totalNotes: number;       // атаки с высотой, включая grace, но без tie-продолжений
  annotatedNotes: number;   // ноты с <fingering> внутри <notations><technical>
  coverage: number;         // annotatedNotes / totalNotes
  hasFingering: boolean;    // coverage >= DETECTION.present
  partial: boolean;         // DETECTION.ignore < coverage < DETECTION.present
}
```

Пороги (`DETECTION`): `present = 0.6`, `ignore = 0.05`.

Обоснование: издательская аппликатура **никогда не бывает на каждой ноте** —
редактор ставит её на сменах позиции, в начале пассажей и в неочевидных местах;
типичная плотность у Henle/ABRSM — 10–40 % нот. Поэтому:

- `coverage ≥ 0.6` — партитура «аппликатурная», не трогаем (F2);
- `0.05 < coverage < 0.6` — **частичная**: авторские цифры фиксируются как
  жёсткие ограничения DP, остальное достраивается (это же делает Ramoneda et
  al., 2022 — «partially annotated scores»);
- `coverage ≤ 0.05` — редкие случайные цифры (например, номер струны), считаем
  партитуру безаппликатурной.

## 6. Архитектура алгоритма

Семь слоёв. Слои 1–3 — подготовка, 4–6 — стоимость, 7 — поиск.

```
MusicXML
  ↓ L1  разбор нот           (adaptive-notes)
  ↓ L2  разделение рук        staff → voice → регистр
  ↓ L3  сегментация           позиционные цепочки, паузы, легато
  ↓ L4  эргономика            Parncutt Table 1 + правила 1–12 (+ Jacobs)
  ↓ L5  вертикаль             аккорды: порядок, растяжение, чёрные клавиши
  ↓ L6  педагогика            гаммы, арпеджио, Альберти, повторы, удержания
  ↓ L7  beam-DP (Viterbi)     детерминированный поиск минимума
FingeringPlan → запись <technical><fingering> → новый .mxl
```

### 6.1 L1. Разбор нот

Специализированный `parseScore` идёт по `<part>/<measure>` и сохраняет
абсолютные смещения каждого `<note>`, временную семантику
`divisions/backup/forward`, локальный onset, исходное написание высоты,
действующие в этой точке key/mode, номера slur, beam-границы и финальные
тактовые черты. Grace-ноты получают onset непосредственно перед основной
нотой. Палец им назначается, и они участвуют в поиске как часть моторного
перехода; из агрегированной статистики `stats.notes` и `thumbOnBlack` они
исключены, чтобы украшения не искажали нагрузку основного текста. В `coverage`
grace остаются атаками и потому учитываются.

### 6.2 L2. Разделение рук

Приоритет сигналов (первый сработавший выигрывает):

1. В одной партии с двумя нотоносцами базовое правило:
   `<staff>1</staff>` → правая, `<staff>2</staff>` → левая.
2. В двух одностановых партиях первая считается правой рукой, вторая — левой;
   последующие партии не относятся автоматически к фортепианному слою и
   пропускаются с `warning`.
3. Cross-staff — исключение из базового правила: если один voice появляется
   на обоих нотоносцах и не менее 75 % его нот живёт на одном из них, весь voice
   сохраняет доминирующую руку. `<staff>` в таком случае описывает печать, а не
   исполнителя. Это устраняет прыжки одного голоса между руками в Severance.
4. Одна нотная строка, два голоса (`<voice>`): это сжатая запись двух рук —
   так печатают Hanon и школьные этюды. Верхний по средней высоте голос
   отдаётся правой руке. Проверено на реальном файле: без этого правила обе
   линии попадали в одну руку, октавные пары заставляли повторять один и тот же
   палец, и совпадение с авторской аппликатурой падало до нуля.
5. Одна строка, один голос: если диапазон укладывается в две октавы — это одна
   рука, и какая именно, говорит ключ (`<clef><sign>`: F → левая, G → правая).
   Диапазон шире двух октав означает запись двух рук на одной строке: делим по
   до первой октавы.

Кроссинг рук (левая выше правой) не запрещаем: он влияет только на
геометрию, а стоимость считается внутри каждой руки независимо.

После базового определения рук допускается одна консервативная **unique
cross-hand edge transfer**. Она работает только в одной фортепианной партии с
двумя нотоносцами, когда одна рука получила физически невозможную диаду, другая
уже атакует на том же onset и существует ровно одно непересекающееся разбиение,
в котором обе руки имеют строгую допустимую форму. Grace, tie, активная slur,
`<arpeggiate>`, авторская аппликатура, пересекающееся удержание и ранняя следующая
атака запрещают перенос. При двух допустимых предложениях алгоритм ничего не
угадывает и сохраняет warning. Решение симметрично для RH→LH и LH→RH и
фиксируется в trace как `crossHandTransfer`.

Это исполнительское назначение руки, а не переписывание издательской нотации:
исходный `<staff>` остаётся прежним; меняются `plan.hands` и placement
автоматической цифры. Общий и неоднозначный voice-leading между руками не входит
в текущие гарантии.

### 6.3 L3. Сегментация

Внутри руки строим `HandEvent[]` и режем их на **сегменты**: границей считается
пауза `gap ≥ FINGERING_SEARCH.resetGap`
(по умолчанию 1 четверть — за это время рука свободно переставляется).
На границе сегмента стоимость перехода обнуляется, кроме мягкого штрафа за
дальний скачок, — это соответствует наблюдению Parncutt, что правила смены
позиции описывают **легатную** игру (сноска 20 в статье).

Пальцевое legato выводится только из явного `<slur>`. Простое соприкосновение
длительностей без `staccato` означает связную фактуру, но не доказывает
непрерывность одним пальцем и не создаёт жёсткого ограничения. Для двух
соседних одиночных нот под slur действует M6 (§6.6.6); фразовая лига над
движущимися аккордами остаётся мягким контекстом, потому что связать каждым
якорным пальцем все голоса одновременно часто физически невозможно.

Совпадение onset ещё не доказывает, что все ноты образуют физический аккорд
одной формы руки. Поэтому реализация использует двухступенчатую проверку:

1. сначала весь onset проверяется как **строгий общий аккорд**; если существует
   допустимая форма, она имеет приоритет и голоса не разделяются;
2. только если общая форма физически невозможна и присутствует более одного
   MusicXML `voice`, вертикаль делится по `partId + voice`; каждый слой обязан
   иметь собственную допустимую форму. Пальцы между слоями могут повторяться,
   потому что это модель арпеджирования/педального подхвата, а не одновременного
   зажатия всей вертикали.

`HeldFinger[]` также хранит `voice`. Конфликт с новой атакой **того же голоса**
остаётся жёстким запретом. Несовместимое удержание другого голоса освобождается
с конечной, **pedal-aware и role-aware** ценой. Парсер строит абсолютную
timeline правой педали внутри партии: `start/change/resume` нажимают,
`stop/discontinue` отпускают, `continue` не меняет состояние; учитываются
`<direction><offset>` и playback-форма `<sound damper-pedal="yes|no|number">`.

Цена межголосового release зависит от положения отпускаемого слоя относительно
нового события:

| слой | под явно активной педалью | без подтверждённой педали |
|---|---:|---:|
| нижний бас | 1 | 2 |
| внутренний голос | 3 | 8 |
| верхний голос | 4 | 12 |

Басовое снятие остаётся возможным и без записанного знака: издатели часто не
дублируют педаль в MusicXML. Верхний и внутренний голос без педали получают
штраф порядка полной смены позиции, поэтому обычная двухголосная полифония
сохраняет пальцевое удержание; конечность цены оставляет физически невозможной
вертикали честный артикулированный выход. Это не ослабляет `MinPrac/MaxPrac`
внутри слоя и не применяется, если сам слой неиграбелен.

Gold-тест инвенционной фактуры без педали защищает верхний голос от тихого
повторного занятия пальца. Pedal-aware изменение и unique cross-hand fallback
вместе сохраняют полное покрытие корпуса: 23 375/23 375 атак, 0 warnings.

### 6.4 L4. Эргономика: модель Parncutt (1997)

База — «An Ergonomic Model of Keyboard Fingering for Melodic Fragments»
(Music Perception 14(4), 341–382). Модель задаёт таблицу растяжений между
парами пальцев **правой** руки в полутонах:

| Пара | MinPrac | MinComf | MinRel | MaxRel | MaxComf | MaxPrac |
|---|---:|---:|---:|---:|---:|---:|
| 1-2 | −5 | −3 | 1 | 5 | 8 | 10 |
| 1-3 | −4 | −2 | 3 | 7 | 10 | 12 |
| 1-4 | −3 | −1 | 5 | 9 | 12 | 14 |
| 1-5 | −1 | 1 | 7 | 10 | 13 | 15 |
| 2-3 | 1 | 1 | 1 | 2 | 3 | 5 |
| 2-4 | 1 | 1 | 3 | 4 | 5 | 7 |
| 2-5 | 2 | 2 | 5 | 6 | 8 | 10 |
| 3-4 | 1 | 1 | 1 | 2 | 2 | 4 |
| 3-5 | 1 | 1 | 3 | 4 | 5 | 7 |
| 4-5 | 1 | 1 | 1 | 2 | 3 | 5 |

Отрицательные значения для пар с большим пальцем — это перекладывание:
`MinPrac(1,3) = −4` означает, что 3-й палец может пройти над большим на
4 полутона вниз (правая рука).

Матричная форма из Приложения статьи (строка `f` — первый палец, столбец `g` —
второй), которую и реализуем напрямую:

```
MaxPrac                MaxComf               MaxRel
 0 10 12 14 15          0  8 10 12 13         0  5  7  9 10
 5  0  5  7 10          3  0  3  5  8        -1  0  2  4  6
 4 -1  0  4  7          2 -1  0  2  5        -3 -1  0  2  4
 3 -1 -1  0  5          1 -1 -1  0  3        -5 -3 -1  0  2
 1 -2 -1 -1  0         -1 -2 -1 -1  0        -7 -5 -3 -1  0
```

`MinX(f,g) = −MaxX(g,f)`. Левая рука — та же таблица с инверсией знака
интервала (`i → −i`).

**Правила и веса** (реализуются как чистые функции, каждая со своим тестом из
примеров статьи):

| # | Правило | Стоимость |
|---|---|---|
| 1 | Stretch | `i > MaxComf → 2·(i − MaxComf)`; `i < MinComf → 2·(MinComf − i)` |
| 2 | Small-Span | `i < MinRel`: с большим пальцем `MinRel − i`, без него `2·(MinRel − i)` |
| 3 | Large-Span | `i > MaxRel`: с большим пальцем `i − MaxRel`, без него `2·(i − MaxRel)` |
| 4 | Position-Change-Count | полная смена позиции 2, половинная 1 |
| 5 | Position-Change-Size | размер смены в полутонах относительно `MinComf`/`MaxComf` для крайних пальцев тройки |
| 6 | Weak-Finger | 1 за каждое использование 4 или 5 |
| 7 | Three-Four-Five | 1 за каждую последовательность из 3, 4, 5 в любом порядке |
| 8 | Three-to-Four | 1 за переход 3 → 4 |
| 9 | Four-on-Black | 1, если 3 и 4 подряд, 3 на белой, 4 на чёрной |
| 10 | Thumb-on-Black | 1 за большой на чёрной, +2 если предыдущая белая, +2 если следующая белая |
| 11 | Five-on-Black | 0, если соседи тоже чёрные; +2 за белую предыдущую; +2 за белую следующую |
| 12 | Thumb-Passing | 1 за перекладывание на одном уровне (бел→бел, чёрн→чёрн); 3, если нижняя нота белая и играется не большим пальцем, а верхняя чёрная под большим |

Смена позиции (правило 4) считается по тройкам нот: она есть, когда интервал
между 1-й и 3-й нотами выходит за `MinComf`/`MaxComf` соответствующей пары
пальцев; **полной** она считается, если средняя нота играется большим пальцем,
её высота лежит между крайними, и интервал крайних выходит за
`MinPrac`/`MaxPrac`. Особый случай из статьи: смена пальца на повторяющейся
ноте через одну (C-F-C = 2-5-1) — половинная смена размера 0.

**Повтор пальца.** В исходной модели пары вида `f-f` запрещены совсем, и это
принципиально: без запрета динамическое программирование ставит один палец на
всю линию — такой путь ничего не стоит. Вместо жёсткого запрета введён штраф
`sameFinger`, у которого три градации: повтор той же ноты — 0, скольжение с
чёрной клавиши на белую (Jacobs) — 1, перенос пальца внутри позиции — 8. Через
скачок шире квинты и между аккордами (последовательность октав играют одной
формой руки) штраф снимается.

**Уточнения Jacobs (2001)**, которые берём:

- разрешаем **повтор одного пальца** на повторяющейся ноте (в исходной модели
  запрещён) и «скольжение» с чёрной на белую тем же пальцем;
- в правиле 4 не начисляем очки, если между тройкой стоит пауза ≥ `resetGap`.

MusicXML умеет кодировать немую подмену через `substitution="yes"`, но текущий
план намеренно не содержит фиктивного флага подмены. Одного атрибута
недостаточно: нужно вывести исходный и новый пальцы, момент смены и отдельно
проверить голосоведение удерживаемой вертикали. Такая модель остаётся
самостоятельным расширением, а не «зарезервированным» полем без семантики.

**Размер руки.** Parncutt прямо указывает, что таблицу можно масштабировать
(«для меньшей руки умножить примерно на 0.9»). Опция `handSpan` выбирает
`{small: 0.9, medium: 1.0, large: 1.1}` со значением `medium` по умолчанию;
масштабируются только `Max*`/`Min*` (с округлением к целому полутону), веса
правил не меняются.

### 6.5 L5. Вертикаль: аккорды

Parncutt моделирует только одноголосие. Полифонию берём по Al Kasimi, Nichols
& Raphael (2007): состояние DP — **множество** пальцев физического аккорда,
стоимость складывается из вертикальной и горизонтальной части. Общая
onset-вертикаль всегда проверяется первой; описанный в §6.3 split-by-voice
является строго ограниченным fallback, а не способом обойти неудобный, но
играбельный аккорд.

Вертикальные ограничения (жёсткие, отсекают состояния) применяются ко всему
строгому аккорду, а в fallback — отдельно к каждому `voice`:

1. Пальцы внутри физического слоя уникальны; между последовательными
   voice-слоями могут повторяться.
2. Порядок пальцев монотонен порядку высот внутри слоя.
3. Для каждой пары нот слоя интервал ∈ `[MinPrac, MaxPrac]` соответствующей
   пары пальцев — иначе слой физически не берётся.

Вертикальная стоимость: сумма правил 1–3 (Stretch/Small-Span/Large-Span) по
всем соседним парам физического слоя + правила 6, 10, 11 по каждому пальцу.
Split-by-voice дополнительно получает одну `Position-Change-Count` на каждую
передачу между слоями: fallback допустим, но не становится бесплатным способом
избежать строгого аккорда.

Горизонтальная стоимость между аккордами: считаем по «якорям» — верхняя нота с
верхней, нижняя с нижней (мелодический и басовый голос ведутся раздельно), плюс
штраф за пересечение, если множества пальцев требуют невозможного скачка.

Более 5 нот в руке (например, арпеджированный аккорд, записанный вертикально) —
берём 2 нижние и 3 верхние, остальные во внутреннем плане наследуют палец
ближайшей по высоте ноты, но их цифры не печатаются; в `warnings` уходят номера
тактов. Если даже оставшаяся вертикаль не имеет допустимой формы по
`MinPrac/MaxPrac`, всё событие подавляется: генератор не выдаёт физически
ложную аппликатуру ради формальной полноты.

### 6.6 L6. Педагогика и теория музыки

Здесь эргономика дополняется тем, чему реально учат. Каждый паттерн даёт
**приор** (отрицательную стоимость выбранному варианту), а не жёсткий
переопределяющий выбор, — чтобы DP мог отказаться от паттерна там, где
контекст (соседний скачок, аккорд в другой руке) делает его дороже.

Фактические приоры: гамма `−20`, пятипальцевая ячейка `−20`, арпеджио `−10`,
точное остинато `−20`, Альберти `−3`, чередование/сохранение пальца на
повторе `−2/−1`. Их абсолютные значения не являются «баллами качества»:
отчёт отдельно показывает положительную эргономическую стоимость и
педагогическую поправку.

Формально это одна аддитивная objective, но масштаб весов важен: штрафы
Parncutt обычно измеряются единицами, поэтому `−20` внутри распознанного
паттерна **доминирует ранжирование**, а не служит слабой подсказкой.
Это осознанная продуктовая политика обучающего инструмента: сначала
`MinPrac/MaxPrac` и остальные hard-ограничения отсекают физически ложные
варианты, затем канон школы выбирает семейство аппликатур, а эргономическая
стоимость различает допустимые варианты внутри этого семейства и остаётся
понятной пользователю оценкой нагрузки. Вне паттерна ранжирование снова
определяет эргономика.

#### 6.6.1 Гаммы

Детектор: ≥ `PEDAGOGY.scaleRun` (8) последовательных нот в одном направлении,
все интервалы 1–2 полутона, множество высотных классов вкладывается в
диатонический звукоряд (мажор / натуральный / гармонический / мелодический
минор). Тональность берётся из действующих **у первой ноты паттерна**
`<key><fifths>/<mode>`, но проверяется по фактическим высотам. Поэтому смена
ключа внутри файла не наследует ошибочно первый глобальный ключ, а мажор не
подменяется относительным минором.

Каноническая аппликатура **выводится**, а не хардкодится, из трёх правил
школы (Clementi 1801, Czerny op. 500, Hanon, ABRSM/RCM scale manuals):

1. большой палец никогда не встаёт на чёрную клавишу;
2. между двумя большими пальцами лежит группа из 3 или 4 нот (пальцы 1-2-3 или
   1-2-3-4);
3. 4-й палец в октаве используется ровно один раз (в обеих руках — кроме
   гамм, где обе группы четырёхнотные, например F-dur в правой).

Для каждой тональности решается маленькая задача расстановки: разбить 7 ступеней
октавы на группы 3+4 или 4+3 так, чтобы начало каждой группы приходилось на
белую клавишу. Решение единственно почти всегда; при двух решениях выбирается
то, где 4-й палец не попадает на ноту, соседнюю с двумя чёрными. Правая рука
считается по возрастанию, левая — по убыванию (зеркально).

Gold-тест M1 сверяет вывод с таблицей стандартных аппликатур: C/G/D/A/E dur
правая `1231234`, F dur правая `1234123`, B dur правая `1231234` (большой на
B и E), Des dur правая `2312341`, левая C/G/D/A/E `5432132`, Bes/Es/As/Des
левая `321432 1` и т. д. Отдельные regression-тесты фиксируют начало и конец
короткого пробега: на краю октавы большой палец не изображает несуществующее
подкладывание.

#### 6.6.2 Пятипальцевые учебные ячейки

У Parncutt штраф Weak-Finger систематически сжимает номер пальца: в Hanon
модель слишком часто заменяла `3→2`, `4→3`, `2→1`, хотя цель упражнения —
работа 4-м и 5-м в неизменной позиции. Универсальный детектор, не знающий
названия файла, распознаёт одну beam-группу (либо цельный такт без beam):

- одноголосные равные быстрые длительности без пауз;
- не менее 7 атак, ровно 5 разных высот;
- общий диапазон не шире 9 полутонов;
- одна и та же высота всегда получает один палец.

Высоты сортируются и отображаются на `1…5` в правой, `5…1` в левой. Детектор
выполняется раньше короткого арпеджио, чтобы трёхнотные подстроки не разрывали
учебную ячейку. Gold-тест проверяет RH/LH-зеркало, октавную транспозицию,
нулевую смену позиции внутри ячейки и независимость уже выбранного префикса от
следующего такта.

#### 6.6.3 Арпеджио и ломаные трезвучия

Основной детектор: ≥ 6 непрерывных нот, все высотные классы образуют
распознанное трезвучие/септаккорд (проверяется интервальная структура от
возможного корня, а не только число pitch classes), интервалы 3–5 полутонов,
одно направление. Дополнительно распознаются короткие однонаправленные
фрагменты из 3–4 нот и семинотная арка вверх-вниз: школьный крайний палец
нужен и там, где длинный порог ещё не достигнут.

Канон: правая вверх 1-2-3-(5 на вершине), левая вверх 5-4-2-1 / 5-3-2-1 в
зависимости от того, какой интервал шире. Здесь Parncutt даёт важное
подтверждение: `MinPrac(1,3) = −4` намеренно не позволяет играть арпеджио
пальцевым легато — оно и не играется легато (Gát, Ortmann). Поэтому на
границе группы арпеджио стоимость перекладывания **не** штрафуется: подсказка
`freeBefore` превращает переход 3→1 / 1→3 в локальную границу сегмента.
Gold-тест фиксирует C-dur вверх в обеих руках и не даёт эргономическому штрафу
снова вытеснить школьный рисунок.

#### 6.6.4 Альбертиев бас и остинатные фигуры

Специализированный детектор Альберти: повторяющаяся четырёхнотная фигура вида
«низ-верх-середина-верх» внутри одного трезвучия, ≥ 2 повторения. Приор —
фиксированный паттерн
5-1-3-1 (левая) / 1-5-3-5 (правая) с одинаковым назначением на всех
повторениях: постоянство фигуры важнее локального оптимума (принцип
экономии движения, C.P.E. Bach; в модели Parncutt это выражается через
правило 4).

Общий детектор остинато ищет точный мотив из 3 или 4 событий с одинаковыми
высотами и сохраняет отображение `pitch → finger` во всех повторениях, включая
последний неполный префикс мотива. Именно отсутствие этого слоя давало на
старом Clocks разные формы одной и той же триоли.

#### 6.6.5 Повторяющиеся ноты

- Быстрый повтор (`duration ≤ FINGERING_SEARCH.fastRepeat`, 0.5 четверти) и ≥ 3 повторений
  → приор на смену пальца (Czerny, Hanon). Конкретный цикл 3-2-1 или 4-3-2-1
  текущая модель не фиксирует: он зависит от темпа, динамики и следующей ноты.
- Медленный повтор или повтор под лигой → тот же палец (уточнение Jacobs).

#### 6.6.6 Легато и голосоведение (жёсткие ограничения)

- Внутри `<slur>` две соседние **одиночные** ноты не могут получить один палец
  на разных высотах (иначе legato физически невозможно) — состояние
  отсекается. На аккордовой фразовой лиге это не распространяется на все
  якоря одновременно.
- Нота, продолженная `<tie>`, наследует палец атаки и не участвует в DP.
- Если голос держится, поиск блокирует палец на всю нотированную длительность.
  Конфликт внутри того же `partId + voice` является жёстким; несовместимое
  удержание другого голоса может быть освобождено с конечной ценой
  позиционного/педального перехвата (§6.3).
- Автоматическая подмена пальца не создаётся. Если авторские ограничения и
  удержания не оставляют допустимого состояния, событие деградирует с
  `warning`, а неподтверждённая цифра не печатается.

### 6.7 L7. Поиск: beam-DP

Классический подход (Hart, Bosch & Tsai 2000; Yonebayashi et al. 2007;
Nakamura et al. 2014) — динамическое программирование / Витерби по
последовательности нот. Реализуем beam-search версию:

- **Состояние**: кортеж пальцев последнего события (для одиночной ноты — один
  палец) + палец предпоследнего события (нужен правилам 4, 5, 7, 10, 11 —
  они смотрят на тройки) + занятые держащиеся пальцы с `voice`, высотой и
  временем окончания.
- **Переход**: все допустимые назначения следующего события; вертикальные
  ограничения отсекаются до расчёта стоимости.
- **Стоимость**: `L4 + L5 + приоры L6`, веса правил — из `DEFAULT_WEIGHTS`.
- **Beam**: `FINGERING_SEARCH.beam = 64` состояний на шаг (для одноголосия 5·5 = 25 состояний
  помещаются целиком, отсечения нет; ограничение работает на аккордах).
- **Тай-брейк**: при равной стоимости выигрывает состояние с меньшей суммой
  номеров пальцев, затем лексикографически меньшее — детерминизм (F7).
- **Сложность**: O(N · B · K), где K ≤ 25 для одноголосия. На партитуре в
  3000 нот — единицы миллисекунд; узкое место — не поиск, а regex-парсинг XML,
  который уже кеширован в `scoreAnalyzer`.

Обе руки считаются **независимо**. Merged-output HMM (Nakamura et al. 2014)
объединяет руки, чтобы решать задачу разделения потоков; у нас разделение
уже дано нотоносцами, поэтому связывание рук добавило бы сложность без выигрыша.

### 6.8 Калибровка весов

Стартовые веса — единичные (как в оригинальной статье: суммируются «очки»).
Отклонения от 1.0 допустимы только с обоснованием и тестом:

```ts
const DEFAULT_WEIGHTS = {
  sameFinger: 1,
  stretch: 1, smallSpan: 1, largeSpan: 1,
  positionChangeCount: 1, positionChangeSize: 1,
  weakFinger: 1, threeFourFive: 1, threeToFour: 1,
  fourOnBlack: 1, thumbOnBlack: 1, fiveOnBlack: 1, thumbPassing: 1,
};

const FINGERING_SEARCH = {
  resetGap: 1,
  fastRepeat: 0.5,
  beam: 64,
};

const PEDAGOGY = {
  scaleRun: 8,
  arpeggioRun: 6,
  priors: {
    scale: -20, fiveFinger: -20, arpeggio: -10,
    alberti: -3, ostinato: -20,
    repeatAlternation: -2, repeatSame: -1,
  },
};
```

`DEFAULT_WEIGHTS` принадлежит модели Parncutt, `FINGERING_SEARCH` — общему
solver-контракту в `fingering-types.ts`, а `PEDAGOGY` — модулю распознавания
паттернов. Масштаб руки передаётся опцией `handSpan` (`0.9 / 1 / 1.1`), а не
смешивается с приорами.

Тест чувствительности: изменение любого веса на ±25 % не должно менять
результат gold-тестов M1/M2. Если меняет — паттерн держится на весе, а не на
музыке, и это баг.

## 7. Запись результата

### 7.1 Вставка `<fingering>` в MusicXML

Спецификация (MusicXML 4.0): `<fingering>` живёт в
`<note><notations><technical><fingering>`. В ресурсной версии каждая нота
аккорда получает свою цифру. В PM-версии цифры одновременных голосов одного
стана собраны в одном `<technical>`, иначе importer теряет часть из них.
`alternate="yes"` и текстовые альтернативы удаляются. Для цифры записываются
`placement="above|below"`, `font-size="8"` и `relative-y="2|-2"`.

Правила записи:

- вставка **точечная**, через позиции регулярного разбора: содержимое
  `<note>` не переписывается, добавляется только недостающий узел. Это
  сохраняет форматирование, `<beam>`, `<lyric>`, `default-x` и всё остальное;
- если у ноты уже есть `<notations>` — добавляем `<technical>` внутрь него;
  если есть `<technical>` — добавляем `<fingering>` внутрь; если `<fingering>`
  уже есть — **не трогаем** (идемпотентность, F6);
- порядок дочерних элементов `<notations>` в схеме свободный, но `<technical>`
  ставим после `<articulations>` — так пишет MuseScore, значит так точно
  читается;
- `placement`: `above` для правой руки (staff 1), `below` для левой — принятая
  издательская норма;
- автоматически созданные цифры имеют `font-size="8"`: они немного меньше
  исходного нотного текста и не перетягивают внимание в плотной фактуре;
- `relative-y="2"` для правой и `relative-y="-2"` для левой добавляет небольшой
  зазор от ноты, не фиксируя абсолютную координату;
- `default-x`/`default-y` не пишутся: горизонтальную и финальную вертикальную
  раскладку выполняет гравировщик, который знает лиги, штрихи и тактовые черты;
- уже существующие авторские `<fingering>` не переписываются и не получают
  автоматически ни `font-size`, ни `relative-y`: редакционная типографика
  исходника неприкосновенна;
- вставка идёт целыми строками с отступом окружающего файла — сгенерированный
  `.mxl` открывается в редакторе так же аккуратно, как экспорт нотатора;
- на продолжении лиги (`<tie type="stop">`) и на «лишних» нотах сверхшироких
  аккордов палец известен модели, но **не печатается**: звук не берётся заново,
  и цифра там — визуальный шум, которого нет ни в одном издании;
- в `<identification><encoding>` добавляем
  `<software>pianomarvel fingering</software>` и `<miscellaneous-field
  name="fingering-source">auto</miscellaneous-field>` — чтобы происхождение
  цифр было видно в файле, а не только в UI.

### 7.2 Новый `.mxl`

Формат по спецификации W3C: zip, первым элементом **несжатый** `mimetype` с
содержимым `application/vnd.recordare.musicxml`, затем
`META-INF/container.xml` с `<rootfile full-path="..."
media-type="application/vnd.recordare.musicxml+xml"/>`, затем сама партитура и
прочие ресурсы.

Реализация — через системный `zip` (как уже используется `unzip` в
`scoreAnalyzer.ts`), в два прохода:

```
zip -X -0 out.mxl mimetype          # первый элемент, без сжатия
zip -X -r out.mxl META-INF <score>  # остальное, DEFLATE
```

Оригинальный архив распаковывается во временную папку
(`scratch`/`os.tmpdir()`), подменяется **только** файл партитуры, все прочие
элементы (изображения, `container.xml`, дополнительные rootfile) переносятся
как есть. Если в оригинале не было `mimetype` — создаём его сами.

Вход `.musicxml`/`.xml` (несжатый): на выходе всё равно **`.mxl`** — так
просил заказчик и так меньше весит; исходный текстовый файл остаётся на месте.

### 7.3 Куда кладём файл

```
<папка автора>/<папка композиции>/
  gymnopedie-no-1.mxl          ← оригинал, не тронут
  fingered/
    gymnopedie-no-1.mxl        ← ресурсная версия
    piano-marvel/
      gymnopedie-no-1.mxl      ← версия для загрузки в PM
```

**Две целевые версии на композицию.** Любая пересборка — хоть
достройка недостающего, хоть полный перебор поверх авторской аппликатуры —
перезаписывает ресурсный и PM-файлы. Отдельного `.rebuilt.mxl` нет
сознательно: партитуру пересобирают по многу раз, и каждая версия рядом с
исходником превратила бы папку в свалку почти одинаковых файлов. История версий
здесь не нужна — оригинал всегда на месте, а генерация детерминирована и
воспроизводится за десятки миллисекунд.

Два следствия, которые надо соблюдать в коде:

- канонический `score_sources` всегда указывает на исходник; защитный случай
  прямой сборки из уже сгенерированного файла всё равно пишет на его же место, а
  не в `fingered/fingered/`;
- запросы к одному target сериализуются внутри процесса; каждый запуск пишет
  в уникальный `…​.building-<pid>-<uuid>` рядом с целью и переносится `rename`.
  Поэтому параллельные `fill/rebuild` не удаляют staging друг друга, а при сбое
  `zip` прежняя версия остаётся целой.

Подпапка, а не суффикс в имени, — сознательное решение: `findSiblingFiles`
(`server/fileMatcher.ts`) склеивает комплект по совпадению токенов имени, и
файл `gymnopedie-no-1.fingered.mxl` при следующем сканировании конкурировал бы
с оригиналом за роль `xml` (сортировка по имени поставила бы его первым).
Подпапка полностью исключает эту коллизию, при этом путь остаётся очевидным
для пользователя.

### 7.4 Каноническая локальная библиотека корпуса

Все необходимые исходники сведены в одну структуру:

```text
~/Downloads/musescore_sheets/
  <author>/
    <composition-stem>/
      <canonical-stem>.mxl
      <canonical-stem>.mid       # если существует
      <canonical-stem>.mp3       # если существует
      <canonical-stem>.pdf       # если существует
      fingered/
        <canonical-stem>.mxl     # только производный результат
```

На момент приёмки это **21 уникальная партитура и 72 исходных файла**:
21 MXL, 21 MID, 17 MP3 и 13 PDF. Разные аранжировки
`Nothing Else Matters` сохранены в отдельных composition-stem, поэтому
`findSiblingFiles` не может смешать их MXL/MIDI; внутри одного каталога exact
stem теперь также имеет приоритет над fuzzy match. Побайтовые дубли Interstellar
и Moonlight не импортированы вторично. Четыре производных MXL дают **76 файлов
на диске**. Старый
`~/Downloads/fingered/clocks-coldplay.mxl` также не стал каноническим: он был
создан до исправления остинато и содержал 2 531 цифру против 2 571 в текущем
плане. Clocks пересобран из неприкосновенного оригинала в
`musescore_sheets/coldplay/clocks-coldplay/fingered/clocks-coldplay.mxl`;
исходник лежит рядом как
`musescore_sheets/coldplay/clocks-coldplay/clocks-coldplay.mxl`.

После переноса все 18 строк `score_sources` в локальной SQLite-базе указывают
на существующие канонические MXL внутри `<author>/<composition-stem>/` и ни одна
не указывает в `fingered/`. Мигратор сохраняет стабильный stem, переносит весь
bundle, затем транзакционно применяет точные пары old→new без изменения
`updated_at`. Перед живой миграцией создан backup SQLite; после неё 76/76 файлов
сохранили исходную multiset-контрольную сумму, 25/25 MXL прошли ZIP-проверку, а
повторный dry-run дал 0 перемещений. Это часть контракта: перенос файлов без
обновления кеша оставляет UI с валидной строкой таблицы, но неработающими
анализом и сборкой.

## 8. API

### 8.1 `/api/scan` — детекция

Ответ дополняется полем `fingering` внутри `guess`:

```json
{ "files": {...},
  "guess": { "...": "...",
    "fingering": { "totalNotes": 1240, "annotatedNotes": 0,
                   "coverage": 0, "hasFingering": false, "partial": false } } }
```

При отсутствии MusicXML поле отсутствует (не `null`, чтобы UI различал
«не проверяли» и «проверили, нет»).

### 8.2 `/api/upload` — генерация

`UploadMetadata` получает флаг `autoFingering?: boolean` (по умолчанию `false`
на сервере; UI шлёт явное значение). Порядок в обработчике:

1. если `autoFingering !== true` или `files.xml` отсутствует — ничего не делаем;
2. читаем XML, считаем coverage; если `hasFingering` — пропускаем и добавляем
   в сообщение «в партитуре уже есть аппликатура (N %)»;
3. иначе генерируем план, пишем `fingered/<имя>.mxl`;
4. **подменяем** `files.xml` на новый путь перед вызовом `uploadSong` — в Piano
   Marvel уезжает файл с аппликатурой;
5. в кеш (`putScoreSource`) кладём **новый** путь: Adaptive-разбор дальше
   работает с ним, и `<fingering>` ему не мешает;
6. любая ошибка генерации **не срывает загрузку**: логируем, продолжаем с
   оригиналом, дописываем предупреждение в `message`.

Шаг 6 принципиален: аппликатура — улучшение, а не условие загрузки.

### 8.3 Анализ и сборка: два разных вызова

Разделение обязательное (§9.5): анализ ничего не пишет на диск, сборка пишет
ровно один файл и возвращает его путь.

**`POST /api/fingering/analyze`**
`{ "path": "/…/score.mxl" }` или `{ "pieceId": 1234 }` (путь берётся из
`getCache().getScoreSource`) →

```json
{ "path": "/…/score.mxl",
  "report": {
    "coverage": { "totalNotes": 1240, "annotatedNotes": 0, "coverage": 0,
                  "hasFingering": false, "partial": false },
    "measures": [ { "index": 0, "number": "1",
                    "right": { "positionChanges": 1, "cost": 0.3 },
                    "left":  { "positionChanges": 0, "cost": 0.1 } } ],
    "patterns": [ { "kind": "scale", "hand": "R",
                    "fromMeasure": 12, "toMeasure": 15,
                    "label": "гамма Соль-мажор" } ],
    "stats": { "notes": 1240, "rightNotes": 680, "leftNotes": 560,
               "positionChanges": 38, "thumbOnBlack": 0,
               "costPerNote": 1.72, "ergonomicCostPerNote": 1.9,
               "pedagogyAdjustmentPerNote": -0.18, "patternNotes": 342 },
    "existing": { "matched": 0, "total": 0 },
    "warnings": [] },
  "trace": [ { "noteIndex": 318, "measure": 14, "hand": "R", "midi": 75,
               "finger": 4, "pattern": "scale",
               "reasons": [ { "rule": "weakFinger", "points": 1 } ],
               "adjustments": [ { "kind": "scale", "points": -6 } ],
               "alternative": { "finger": 3, "delta": 4.5,
                                "scope": "local" } } ],
  "previewXml": "<?xml version=\"1.0\"?>…" }
```

`previewXml` — полный MusicXML исходной партитуры с аппликатурой текущего плана,
собранный в памяти без записи на диск. UI передаёт его непосредственно в OSMD.
Это намеренно заменяет прежний визуальный контракт `staffNotes`: сокращённый
массив высот и длительностей не мог честно восстановить beams, tuplets,
cross-staff, несколько голосов, лиги, переносы и издательские коллизии.

`trace` — материал для учебной панели §9.3: по одной записи на ноту, каждая с
разбивкой по правилам, педагогическими поправками и локальной чувствительностью
к альтернативному пальцу. Это не обещание второго глобально оптимального пути:
`scope: "local"` явно ограничивает сравнение соседними переходами. Ответ может быть большим, поэтому
`trace` отдаётся только при `?trace=1`; карта и статистика — всегда.

**`POST /api/fingering/build`**
`{ "path": "…", "mode": "fill" | "rebuild", "handSpan": "small|medium|large" }` →
`{ "path": "/…/fingered/score.mxl", "report": { "stats": {...},
"existing": { "matched": 843, "total": 1240 }, "warnings": [] },
"trace": [...], "previewXml": "<?xml version=\"1.0\"?>…",
"editor": "MuseScore 4" }`.

- `mode: "fill"` (по умолчанию) — авторские цифры сохраняются как ограничения,
  достраивается недостающее;
- `mode: "rebuild"` — авторские цифры стираются (`stripFingering`), аппликатура
  строится целиком нашей моделью, а в ответе `existing.matched` показывает
  совпадение с исходной разметкой.

Оба режима пишут **один и тот же** `fingered/<имя>.mxl` и никогда не трогают
оригинал. В ответе приходит `editor` — имя найденного на машине нотатора, им
подписывается кнопка проверки.

### 8.4 `POST /api/pieces/:id/piano-marvel-score` — заменить нотный файл

Кнопка должна менять партитуру **существующей** композиции, а не создавать
дубликат через общий `/api/upload`.

```json
{ "source": "original" }
```

или

```json
{ "source": "fingered", "fingeringMode": "fill" }
```

Успешный ответ:

```json
{
  "success": true,
  "source": "fingered",
  "path": "/…/fingered/score.mxl",
  "message": "Партитура обновлена в Piano Marvel",
  "report": { "stats": {} },
  "trace": [],
  "previewXml": "<?xml version=\"1.0\"?>…",
  "editor": "MuseScore 4"
}
```

Сервер разрешает `original` только в канонический `score_sources.xml_path`.
Для `fingered` он строит производный файл **из этого исходника**, проверяет
контейнер и передаёт ровно возвращённый `path` в поле MusicXML формы
`/uploads/editSong/:id`. Канонический `score_sources` не заменяется производным:
иначе исчезнет выбор исходника, а следующая сборка начнётся с собственного
вывода. Ответ обязан вернуть выбранный `source` и фактически отправленный
`path`; клиент отвергает подтверждение с другим discriminator или пустым
путём.

Основная кнопка `Обновить` в строке сначала предлагает два явных варианта:
`Исходный · без автоцифр` и `С аппликатурой · fingered MXL`. Только после
успешной замены файла она ставит текущий учебный режим в очередь — обучение не
должно пересобираться поверх старой партитуры. Кнопка `Обновить на Piano
Marvel` во вкладке аппликатуры всегда отправляет `source: "fingered"` и
обновляет report/preview из ответа, но не запускает соседний learning-flow.
Loading, ошибка и подтверждение содержат точный путь, а не только сменившуюся
подпись кнопки.

Эксплуатационный контракт также является частью endpoint:

- любой ответ API, включая неизвестный маршрут, имеет JSON-форму `{ "error": "…" }`;
- общий клиентский `requestJson` читает body один раз, сохраняет точное сообщение
  backend, а для legacy plain-text 404 объясняет, что локальный backend устарел,
  вместо показа `JSON.parse SyntaxError`;
- весь score-update выполняется под `withTaskLogger`: журналируются method/path,
  выбранный source, canonical/selected path, открытие editSong, attachment,
  submit и подтверждение Piano Marvel;
- локальный `dev` запускает сервер как `bun --watch run server/index.ts`, поэтому
  Vite HMR не может надолго разойтись с набором backend-маршрутов;
- ошибка attach/submit/подтверждения возвращается как ошибка и не маскируется
  зелёным success-toast.

### 8.5 `POST /api/fingering/open` — проверка результата глазами

`{ "path": "/…/fingered/score.mxl", "reveal": false }` — открывает файл в
нотаторе (`open -a "MuseScore 4"`), при `reveal: true` показывает его в Finder
(`open -R`), ничего не запуская.

Ограничения ручки: только существующие файлы и только расширения `.mxl`,
`.musicxml`, `.xml`. Нотатор ищется в `/Applications` и `~/Applications`
(`server/score-editor.ts`): между версиями выигрывает старшая
(`MuseScore 4` важнее `MuseScore 3`), между программами — MuseScore, потому что
он открывает MusicXML без диалогов импорта; дальше Finale, Sibelius, Dorico.
Если нотатора нет вовсе, файл отдаётся системному обработчику.

Зачем это в продукте, а не в терминале: отчёт показывает цифры, но расстановку
на нотном стане — не сталкиваются ли цифры с лигами, читается ли аппликатура в
плотных местах — видно только в настоящем нотаторе. Путь туда должен быть в
один клик, иначе проверять никто не будет.

## 9. UI

Четыре точки входа, ни одна из которых не ломает основной поток «нашёл файлы →
проверил метаданные → загрузил»:

1. **«Ноты и аппликатура» прямо под названием композиции** — видимый вход без
   догадки, что функция спрятана под иконкой глаза;
2. **чекбокс в акте III** — автоматика при загрузке (§9.1);
3. **вкладка «Аппликатура» в раскрытом плане композиции** — разбор того, что
   получилось, и пересборка (§9.2);
4. **учебная панель «Как подобрать самому»** — объяснение правил на материале
   собственной партитуры (§9.3).

Кнопка строки раскрывает нужную вкладку и запускает анализ при необходимости;
повторное нажатие на ту же «Ноты и аппликатура» сворачивает контент и
синхронно меняет `aria-expanded`. Eye/refresh остаются действиями плана
Adaptive и больше не должны служить неочевидным маршрутом к MXL.

Панель «Способ обучения» теперь разделяет две системы: Adaptive/Predict строят
маршрут занятия, а Fingering Compiler — моторный план. В раскрытии «Как работают
маршрут и аппликатура» четыре общих сигнала объясняют руки, физику, школу и
доставку MXL; CTA «К нотам и аппликатуре» переводит фокус к первой строке
workbench. Каталог открывается с `pageSize = 32` (селектор 8/16/32), поэтому
текущий корпус из 21 композиции виден на одной странице по умолчанию.

### 9.1 Чекбокс (акт III, `MetadataMovement.vue`)

Рядом с «Создать обучающий режим после загрузки», в той же стилистике
`.learning-option`:

> ☑ **Подобрать аппликатуру, если её нет в партитуре**
> Новый `.mxl` с цифрами сохранится рядом с оригиналом, в подпапку `fingered`.
> Оригинал не изменяется.

Состояния:

| Условие | Вид |
|---|---|
| MusicXML не найден | чекбокс `disabled`, подпись «нужен MusicXML» |
| `hasFingering` | чекбокс `disabled` + отметка «в партитуре уже есть аппликатура · 87 % нот» и ссылка «пересобрать своей моделью» → §9.2 |
| `partial` | активен, подпись «в партитуре 23 % нот с аппликатурой — авторские цифры будут сохранены» |
| нет аппликатуры | активен, значение по умолчанию **включён** |

Значение по умолчанию — включён: пользователь загружает партитуры, чтобы
учиться по ним, и «без аппликатуры» — это почти всегда не сознательный выбор,
а свойство экспорта с MuseScore.

### 9.2 Вкладка «Аппликатура» в панели композиции

Панель раскрытой строки таблицы (`.learning-plan-panel` в
`PiecesMovement.vue`) содержит **две вкладки одного документа**:

```
┌ Партитура · Gymnopédie No. 1 ────────────────────────────────┐
│  [ План разучивания ]  [ Аппликатура ]        · · · · · · ·  │
├──────────────────────────────────────────────────────────────┤
│  ... содержимое активной вкладки ...                         │
└──────────────────────────────────────────────────────────────┘
```

Вкладки — не новый компонент библиотеки, а тот же язык, что уже используется в
таблице: `role="tablist"`, стрелки ←/→ между вкладками, `aria-controls`,
сохранение выбранной вкладки на строку в `reactive`-словаре (как
`planPreviews`). Переключение не перезапрашивает данные: анализ аппликатуры
кешируется рядом с планом.

**Что показывает вкладка «Аппликатура»** (сверху вниз):

1. **Состояние источника** — три состояния одной строкой, без модалок:
   «в партитуре нет аппликатуры» / «частичная: 23 % нот» / «полная: 87 % нот».
   Рядом — путь к файлу и, если он уже сгенерирован, `fingered/<имя>.mxl` с
   отметкой времени.
2. **Нотный лист — доминирующий объект вкладки.** `FingeringScore.vue`
   лениво загружает OSMD, получает полный `previewXml`, ограничивает гравировку
   внутренним 1-based индексом выбранного такта и выводит SVG исходной
   MusicXML-нотации. Компонент не пересчитывает высоты и ритм сам; pickup и
   повторяющиеся XML `number` не сдвигают окно, потому что навигация работает
   по внутреннему индексу. Нотные головки получают невидимые hit-targets:
   hover/focus мягко подсвечивает одну ноту и показывает высоту, длительность,
   палец, руку/стан, **мелодическую линию** и контекст tie/tuplet/chord. Термин
   MusicXML `voice` в ученическом UI не показывается без объяснения:
   «мелодическая линия» — независимый ритмический слой на одном стане.
   Совпавшие видимый и скрытый унисоны разных линий объединяются по
   `staff-entry + pitch`, но сохраняют отдельные длительности и пальцы.
3. **Учебный слой текущего такта динамический.** Из полного MusicXML строится
   inventory только тех печатных обозначений, которые действуют или видимы в
   выбранном такте: ключ, ключевые знаки, размер, длительности/паузы,
   аппликатура, альтерации, beams, tuplets, tie/slur, артикуляция, динамика и
   вилки, педаль, арпеджирование, форшлаги, орнаменты, репризы/вольты,
   октавные переносы, tremolo/glissando и авторские unknown-обозначения.
   Состояние протяжённых знаков сканируется от начала партии: если
   `wedge`, `pedal`, `octave-shift`, `dashes`, `bracket`, `slur` или `tie`
   начались раньше и ещё не получили `stop`/`discontinue`, промежуточный такт
   явно помечается как продолжение. Slur изолируется по
   `staff + voice + number`, tie — дополнительно по высоте, поэтому одинаковые
   номера в двух мелодических линиях не конфликтуют.
   Статической легенды «на все случаи» нет: крупная `3` объясняется как триоль
   только в такте, где реально присутствует `<tuplet>`/`<time-modification>`.
   Неизвестное видимое обозначение не угадывается, а получает нейтральную
   подпись с исходным MusicXML-именем.
4. **Ключ, тональность и метр исследуются прямо на стане.** После OSMD-render
   устойчивые VexFlow-группы `.vf-clef`, `.vf-keysignature` и
   `.vf-timesignature` получают hover/focus; рядом остаются доступные chips.
   Для `<key><fifths>` показывается порядок диезов/бемолей и пара
   major/relative-minor по квинтовому кругу. Если `<mode>` задан, выводится
   точная тональность; если mode отсутствует, UI честно показывает два
   кандидата, а не выдумывает лад по одному ключевому знаку.
5. **Счёт ритма** строится по фактическим onset выбранного такта с учётом
   `divisions`, `backup/forward`, `chord`, grace и простого
   `time-modification`. Простое деление объясняется слогами
   `Раз-и, Два-и` / `Раз-та-и-та`, явная триоль — `Раз-три-оль`; составные
   6/8, 9/8 и 12/8 группируются по пунктирной четверти и произносятся
   `Раз-и-а`, без ложного объявления каждой группы триолью. Затакт не
   дополняется воображаемыми нотами. Заимствованный слог `e` из
   англоязычного `1-e-&-a` не транслитерируется как необъяснимое «е»:
   таблица, tooltip ноты, `aria-label` и подпись бегунка используют один
   канонический объект метрической позиции.

   Минимальное разрешение простого метра — восьмые даже для целой ноты:
   в 4/4 ученик произносит `Раз-и-Два-и-Три-и-Четыре-и`, нажимает только на
   `Раз` и видит непрерывное удержание до конца такта. Staccato отделено от
   нотированной длительности: точка получает короткий хвост и подсказку
   «сыграть коротко и отпустить», а не ложную линию удержания.

   Окно 1/3/5 больше не пытается уместить пять полных **учебных таблиц**.
   OSMD при этом честно показывает все выбранные 1/3/5 тактов; компактные
   мини-профили обеих рук выбирают один такт для подробного разбора на полную
   ширину. Внутри активного такта одна общая метрическая шкала и две
   независимые дорожки рук; состояние сохраняет одновременно
   `attack + heldNotes`, поэтому полифония вроде Lumière, такт 5, честно
   говорит «держи 2 и возьми ещё 2».

   START запускает активный такт. Синхронная вертикальная линейка проходит
   поверх фактической OSMD-гравировки выбранного такта внутри диапазона 1/3/5,
   а её badge и активная клетка показывают один и тот же полный счёт
   (`Раз-и`, `Два-та` и т. п.). Hover длинного события показывает не только
   onset: у целой ноты это полный диапазон
   `Раз-и-Два-и-Три-и-Четыре-и`.

   Hover/focus/tap клетки открывает единый `Teleport`-overlay с
   `position: fixed`, viewport collision и структурированными строками
   «счёт / рука / действие / нотированная длительность». Он не участвует в
   layout таблицы и не может вытолкнуть её за рамку.

   Ограничение текущей фазы: смешанные duple+tuplet, quintuplet/sextuplet и
   точная группировка additive meter требуют переменной сетки по долям; они
   перечислены в P8 и не должны называться уже закрытыми.
6. **Навигация по тактам** — крупные «Назад/Дальше», слайдер со всем диапазоном,
   прямой ввод печатного номера такта и клавиши ←/→/Home/End на фокусируемой
   области партитуры. Смена диапазона перерисовывает ровно выбранные 1/3/5
   тактов, а выбор mini-profile меняет только активный учебный detail; границы
   имеют `disabled`, текущее значение сообщается через `aria-valuetext`.
7. **Сводка второго уровня** — карта рук, метрики, распознанные паттерны и
   предупреждения находятся ниже нотного листа в закрытой по умолчанию
   «Диагностике анализа». Одинаковые соседние фигуры агрегируются по
   `kind + hand + label` в диапазоны тактов и показываются компактно, а не
   отдельной карточкой на каждый такт. Предупреждения также свёрнуты и
   сопровождаются счётчиком.
8. **Одно действие в верхней части вкладки.** Read-only анализ запускается
   автоматически при открытии; единственный primary CTA — `Обновить на Piano
   Marvel`. Он выполняет fill-сборку, сохраняет авторские цифры, добавляет
   недостающие, пишет `<каталог композиции>/fingered/<имя>.mxl` и заменяет
   MusicXML существующей композиции по контракту §8.4. Канонический исходник
   остаётся на месте.
9. **Проверка глазами** — после сборки рядом с полным путём появляются два
   текстовых действия: «Открыть в MuseScore» (подпись берётся из имени
   найденного приложения) и «Показать в Finder». Отчёт показывает цифры, но
   расстановку на нотном стане — интервалы, столкновения с лигами, читаемость —
   имеет смысл смотреть в настоящем нотаторе, и путь к этому должен быть в один
   клик, а не через копирование пути.
10. **Предупреждения** — по умолчанию свёрнутая группа с количеством. Длинный
   список не вытесняет нотный стан и основные действия за пределы экрана.
11. **Понятная стоимость** — основной цифрой показана положительная
   `ergonomicCostPerNote`; рядом помещается компактная «пед. скидка −…» или
   «пед. надбавка +…». Полная objective с крупными отрицательными приорами не
   называется ученической «ценой ноты» и остаётся технической диагностикой.

Во время ленивой загрузки OSMD место нотного листа занимает skeleton той же
высоты; ошибка рендера остаётся внутри карточки с понятным повтором, не ломая
всю раскрытую строку. `ResizeObserver` перерисовывает лист после реального
изменения ширины, а очередь версий отбрасывает устаревший async-render при
быстром движении слайдера.

`mode: rebuild` остаётся API/bench-возможностью для диагностики и сравнения с
авторской разметкой, но не конкурирует с основным пользовательским действием
отдельной кнопкой.

### 9.3 Учебная панель «Как подобрать самому»

Главная причина, по которой алгоритм правило-ориентированный, а не нейросетевой
(§14): **каждую цифру можно объяснить**. Поэтому движок возвращает не только
палец, но и трассировку — какие правила и с каким вкладом сработали.

Трассировка первой доступной ноты выбранного такта открывается в свёрнутой
карточке. Точная головка уже доступна через hover/focus и обучающую подсказку;
связать выбор этой головки с полным rule-trace и подсветить все ноты, где
сработало одно правило, остаётся расширением:

```
Такт 14 · правая рука · ре♯5 · палец 4

Почему 4
  ▸ гамма Си-мажор, восходящий пассаж          −6.0   паттерн школы
  ▸ большой палец не встаёт на чёрную            0     правило 10
  ▸ 4-й палец — единственный раз в октаве      +1.0   правило 6 (слабый палец)
  ▸ без смены позиции до си                      0     правила 4–5

Альтернатива: палец 3 дороже на 4.5 очка — потребовал бы
смены позиции внутри пассажа (правило 4, полная смена = 2 очка).
```

Рядом — свёрнутый по умолчанию блок **«Правила, по которым это делают руками»**:
короткий конспект школы, каждый пункт с одним предложением «зачем» и, где
уместно, с миниатюрой на нотном стане:

1. **Сначала опорные точки.** Найдите в пассаже места, где рука обязана
   поменять позицию, — скачки шире квинты, смены направления, начало фраз.
   Аппликатура строится между ними, а не нота за нотой.
2. **Большой палец — на белую.** В гаммах и пассажах 1-й палец не встаёт на
   чёрную клавишу (Clementi, Czerny). Это единственное правило, которое
   почти никогда не нарушают.
3. **Группы по 3 и 4.** Между двумя большими пальцами лежит 3 или 4 ноты.
   В октаве гаммы 4-й палец встречается ровно один раз.
4. **Следующая нота — следующий палец.** Соседние ступени играются соседними
   пальцами, пока это не требует растяжения (принцип Türk, в модели — правила
   2 и 3).
5. **4 и 5 — слабые.** На сильную долю, длинную ноту и трель их стараются не
   ставить; последовательность 3-4-5 подряд неудобна (правила 6 и 7).
6. **Легато нельзя сыграть одним пальцем.** Под лигой два разных звука требуют
   двух разных пальцев. Немая подмена существует в исполнительской практике,
   но автоматический генератор её пока не выводит.
7. **Аккорд берут «как есть».** Пальцы в аккорде не перекрещиваются, а крайние
   ноты должны укладываться в вашу растяжку — проверьте её на квинте и октаве.
8. **Повторяющаяся фигура — одна аппликатура.** Альбертиев бас, ломаное
   трезвучие, секвенция: постоянство важнее локального удобства (C.P.E. Bach).
9. **Проверяйте медленно и с закрытыми глазами.** Если рука сама не находит
   следующую клавишу — аппликатура неудобна независимо от теории.

Каждый пункт связан с конкретным правилом модели, поэтому текст — не абстракция:
включив «подсветку правила», пользователь видит все ноты партитуры, где это
правило сработало. Это и есть учебный режим: не «вот тебе цифры», а
«вот почему эти цифры и как их получают руками».

### 9.4 Визуальный язык

Стиль — уже принятый в проекте Payard-подобный минимализм (см. таблицу и
`src/styles/table.css`), без нового визуального словаря:

- **вкладки**: капсула с подложкой, активная вкладка — заполненный сегмент
  точной формы, переход `300ms cubic-bezier(0.65, 0.05, 0, 1)`; ровно та же
  механика, что у сегментированной группы eye/refresh;
- **кнопки действий**: существующая модель Payard CTA — цветная капсула по
  умолчанию, при наведении оболочка белеет за 300 мс, подпись уезжает к левому
  краю за 500 мс, отдельная капсула поднимается снизу с blur → clear;
  геометрия не меняется, `transform: none` на внешнем слое;
- **нотный лист**: белая спокойная поверхность и чёрная издательская
  гравировка OSMD; брендовый синий используется в оболочке, фокусе, слайдере и
  временной подсветке одной головки, но не перекрашивает нотный текст постоянно;
- **обозначения**: легенда выводит только семантику текущего такта, включая
  протяжённые знаки, начавшиеся раньше и ещё действующие здесь; маленькие `1–5`
  у ноты подписываются как аппликатура, а крупная `3` над/под группой — как
  триоль лишь при реальном tuplet. Ключ/знаки/размер имеют точный hover/focus
  по SVG-группе и дублирующий discoverable chip;
- **overlay**: контрастная карточка до 320 px в едином portal-слое,
  `position: fixed`, `z-index: 10000`, измерение фактического размера,
  flip/shift относительно viewport и обычный UI-шрифт 13 px. Она не участвует
  в геометрии партитуры/таблицы; контент разделён на счёт, руку, действие и
  факты вместо одной длинной технической строки;
- **ритмическая строка**: учебная последовательность
  `выбери такт → скажи вслух → включи метроном → следуй двум дорожкам рук`;
  OSMD показывает выбранные 1/3/5 тактов, компактный обзор выбирает один из них,
  а подробная шкала всегда одна и занимает всю ширину. На desktop доли —
  равные вложенные колонки, на mobile каждая доля становится отдельным блоком
  с touch-cell не уже 40 px;
- **типографика MXL**: автоматически добавленные цифры имеют `font-size="8"`
  и мягкий `relative-y ±2`; авторские цифры сохраняют исходные атрибуты;
- **движение**: анимируются только `opacity`, `transform`, `filter`; всё
  выключается в `prefers-reduced-motion`;
- **тёмная/светлая тема** — через существующие токены, без новых переменных.

### 9.5 Порядок работы: автоматический анализ, одно явное действие

Открытие вкладки автоматически выполняет read-only анализ и показывает preview:

```
открыть вкладку → analyze + OSMD preview
               → [Обновить на Piano Marvel]
               → fill-build → проверка source/path → editSong → полный путь
```

Анализ не имеет побочных эффектов. Единственный явный write-action создаёт новый
файл и всегда сообщает полный путь; ошибка на любом шаге не превращается в
успех. Автоматический сценарий из §9.1 выполняет ту же последовательность.

останавливает обход на любом каталоге с basename `fingered`, ничего не
записывает и печатает JSON с числом атак/подавлений, видом эталона,
авторским совпадением, паттернами, предупреждениями и временем. Стоимость
в каждой строке всегда разложена на три поля: `costPerNote` — полная objective,
`ergonomicCostPerNote` — стабильная физическая нагрузка, и
`pedagogyAdjustmentPerNote` — вклад распознанных школьных паттернов. Именно
эргономическая колонка сохраняет сравнимость снапшотов, если состав или вес
приоров снова изменится:

```bash
bun run bench:fingering -- ~/Downloads/musescore_sheets
```

Это делает §2.3 воспроизводимым локально. Метрика остаётся наблюдательной:
общий quality gate появится только вместе с лицензированным переносимым
корпусом, а не с путём в домашнем каталоге одного разработчика.

| Межголосовой release выдаст непальцевое legato без реальной педали | M9: MusicXML pedal timeline, штрафы bass/inner/upper `1/3/4` под педалью и `2/8/12` без неё, отдельный no-pedal polyphony gold |

| Две редакции одной песни перезапишут или смешают файлы | отдельный composition-stem, запрет overwrite, scoreId-суффикс, exclusive `.pianomarvel-download.lock`, пакетный rollback переноса и exact-before-fuzzy matcher |

### 12.1 Что вскрылось только на реальных партитурах

Часть дефектов не воспроизводилась на первых синтетических фикстурах и нашлась
только при прогоне по локальной библиотеке. Они стоят того, чтобы остаться в
документе:

1. **Свободный повтор пальца ломает всю модель.** Без штрафа `sameFinger`
   динамическое программирование ставит один палец на всю линию — это путь
   нулевой стоимости. Запрет в оригинальной статье оказался не деталью, а
   несущей конструкцией.
2. **Голоса важнее регистра.** На одной нотной строке с двумя голосами (Hanon
   condensed) деление рук по высоте отправляло обе линии в одну руку;
   октавные пары заставляли повторять палец, и совпадение с авторской
   аппликатурой падало до нуля. Правильный сигнал — `<voice>`.
3. **Не всякая назначенная цифра должна печататься.** На продолжении лиги звук
   не берётся заново, и цифра там — визуальный шум. Отсюда `plan.suppressed`:
   палец известен модели, но в файл не попадает.
4. **Touching durations не равны slur.** Отсутствие staccato не создаёт
   обязательного пальцевого legato. На реальных аккордовых фактурах это
   превращало нормальный перенос руки в невозможную связанную форму.
5. **Эргономическая цель может конфликтовать с жанром упражнения.** Hanon
   намеренно нагружает 4-й и 5-й пальцы; без отдельной распознаваемой
   пятипальцевой ячейки Weak-Finger сжимал номера даже при полном техническом
   покрытии.
6. **Нотированная длительность не всегда равна времени удержания пальцем.**
   `HeldFinger[]` исправил повторное использование действительно занятого
   пальца, но резервирование до конца duration оказалось чрезмерно строгим для
   выдержанного баса с педалью и аккордов другого голоса. Gymnopédie получила
   аномальные 15,01 очка/ноту, а Moonlight и Running Up That Hill — основную
   массу подавлений. Исправление хранит `voice`: внутри голоса удержание
   жёсткое, между голосами возможен конечный перехват (§6.3), без ослабления
   растяжек.
7. **Совпавший onset не гарантирует физический аккорд.** Ноты разных голосов
   могут быть синхронны на странице, но последовательно перехватываться одной
   рукой. Теперь общий аккорд всегда проверяется первым, а split-by-voice
   разрешён только после его физического отказа и только при допустимости
   каждого отдельного слоя.
8. **Производный корпус нельзя использовать как gold.** Рекурсивный обход
   `fingered/` дал модели 2 571 самосовпадение на Clocks и искусственно поднял
   метрику до 93,1 %. Обход теперь прекращается на basename `fingered`;
   source-only и human-technical агрегаты являются отдельными понятиями (§2.3).
9. **Название метрики обязано совпадать с формулой.** Раньше `costPerNote`
   вычислялся из `ergonomicCost`, хотя продуктовая подпись
   подразумевала полную objective cost с педагогическими приорами. Формула
   исправлена на `objectiveCost / notes`; bench хранит objective, эргономику и
   педагогическую поправку раздельно. UI не выдаёт внутреннюю objective за
   ученическую цену: основной показатель — эргономика/нота, рядом — приор.
10. **Диагностика не должна умножать одну причину.** `warnings.push` внутри
    цикла событий повторял одну строку для одного такта. Отчёт теперь
    агрегирует физические отказы по `measure + hand` и указывает числа событий
    и нот; UI держит предупреждения в свёрнутой группе со счётчиком.
11. **Зарезервированное поле — не реализованная функция.** `substitutions`
    читалось XML-писателем, но поиск его не заполнял. Мёртвый контракт удалён:
    будущая подмена должна сначала получить модель двух пальцев и момента
    смены, а уже затем MusicXML-атрибут и UI.

## 13. Почему первоначальная реализация была не совсем корректна

Первое приближение правильно выбрало основу — таблицы Parncutt, педагогический
слой, beam-DP и точечную запись MusicXML. Ошибки появились на границах слоёв:
локально разумные функции ещё не образовывали честный сквозной контракт.

1. **Статус реализации смешивался со статусом приёмки.** Наличие детектора или
   матрицы и unit-теста считалось доказательством всего музыкального критерия.
   Например, тест вспомогательной функции гаммы не проверял, что тот же рисунок
   переживёт стоимость DP, а заявленная корпусная метрика не имела
   воспроизводимого runner. Теперь PRD разделяет gold-тест, инвариант и
   наблюдательный bench; M7 не является quality gate без переносимого корпуса.
2. **`rebuild` уничтожал эталон до сравнения.** Авторские `<fingering>`
   удалялись перед планированием, поэтому `existing.total` становился нулём и
   UI показывал формально корректную, но бессмысленную метрику. Теперь исходная
   карта пальцев снимается до `stripFingering` и передаётся в план отдельно.
3. **В состоянии поиска сначала не хватало долговременных музыкальных фактов,
   а затем нотированное удержание стало слишком жёстким.** Учёт только соседних
   атак позволял повторно занять палец действительно удерживаемой ноты.
   `HeldFinger[]` закрыл эту ошибку, но заблокировал палец на всю duration даже
   между независимыми голосами и там, где звук уже держит педаль. Правильная
   модель сохраняет долговременное состояние вместе с `voice`: конфликт своего
   голоса остаётся жёстким, а несовместимый другой голос освобождается с
   конечной ценой педального/позиционного перехвата. Дополнительно общий аккорд
   всегда проверяется до голосового fallback, поэтому удобная эвристика не
   отменяет физику настоящей вертикали.
4. **Идентичность tie была слишком слабой.** Одной высоты недостаточно:
   унисон может одновременно звучать в нескольких голосах и партиях. Источник
   продолжения теперь ищется по
   `partId + staff + voice + midi` и только среди нот с `tieStart`.
5. **Нотоносец ошибочно принимался за руку.** `staff 1 = above` и
   `staff 2 = below` неверны для одностановой левой руки, двух одностановых
   партий и сжатой двухголосной записи. Разделитель теперь сначала выводит
   руку, сохраняет её в `plan.hands`, и XML placement берётся из этого решения.
6. **Атомарная запись была спутана с взаимным исключением.** Один общий
   `.building` защищал финальный `rename`, но параллельные сборки удаляли
   временный файл друг друга раньше. У каждой сборки теперь уникальный staging,
   а запросы к одному абсолютному target сериализуются внутри процесса.
7. **Возможность формата принималась за реализованную семантику.** Наличие
   `substitution="yes"` в MusicXML не означает, что достаточно поставить флаг:
   подмена требует двух пальцев, времени смены и проверки удерживаемых голосов.
   Мёртвое поле удалено из плана и XML-писателя; автоматическая substitution
   исключена из текущих гарантий.
8. **Внутренняя оценка показывалась как объективная истина.** Отрицательные
   педагогические приоры смешивались с эргономической ценой, локальная замена
   называлась «лучшей альтернативой», нулевая нагрузка рисовалась как полный
   столбик, а после сборки UI мог оставить старую трассировку. Теперь стоимость
   правил и педагогические поправки разделены, альтернатива помечена
   `scope: "local"`, нулевая карта действительно пуста, а ответ build обновляет
   трассировку.
9. **Не хватало враждебных интеграционных примеров.** Happy-path фикстуры не
   ловили параллельные build, одинаковый MIDI в разных голосах, длительное
   удержание, одностановую LH, третью партию и невозможную вертикаль. Эти случаи
   теперь зафиксированы отдельными regression-тестами с проверкой не только
   плана, но и напечатанного XML.
10. **Соприкасающиеся длительности ошибочно считались обязательным legato.**
    Именно это породило показанный пользователю длинный список «физически
    допустимая форма не найдена»: обычная последовательность без staccato
    превращалась в жёстко связанную цепь, занятые пальцы накапливались, а
    аккордовые якоря требовали невозможного растяжения. В диагностическом
    корпусе это давало 143 отказа в Another Love, 152 в Gymnopédie и 172 в
    Radioactive. Теперь жёсткое M6 возникает только между одиночными нотами
    внутри явного `<slur>`; фразовая лига над аккордами остаётся мягкой.
11. **Тональность бралась один раз на весь документ.** При смене ключа и в
    файлах с неявным mode мажорный пассаж мог распознаться как относительный
    минор. `keyFifths/keyMode` теперь живут на ноте и входят в границу паттерна;
    source spelling сохраняется отдельно от MIDI.
12. **Печатный staff принимался за физическую руку.** Cross-staff voice в
    Severance прыгал между L/R вместе с нотоносцем. Теперь голос, устойчиво
    принадлежащий одной стороне, сохраняет доминирующую руку даже при переносе
    головки на другой staff.
13. **Повторяемость фактуры не была частью состояния.** Локально дешёвый DP
    давал разную форму одной и той же триоли Clocks, а короткие арпеджио не
    достигали порога длинного детектора. Добавлены точные остинато 3/4 с
    хвостовым префиксом, короткие/арочные арпеджио и приоритет постоянного
    `pitch → finger`.
14. **Parncutt оптимизирует удобство, а упражнение иногда оптимизирует
    развитие.** В Hanon штраф Weak-Finger систематически заменял
    `3→2`, `4→3`, `2→1`. Структурный детектор пяти высот поднял совпадение с
    автором с 535/1047 до 789/1047, не проверяя title, номер упражнения или
    конкретные высоты.
15. **Сильнейший локальный gold был невидим bench.** В файле Piano Major
    Scales 870 цифр лежат как numeric lyrics, а не `<technical><fingering>`.
    Адаптер принимает их только при плотности ≥60 %, минимум 8 значениях и
    отсутствии обычного текста; одиночная цифра песни не становится
    псевдо-эталоном. Фактическое совпадение — 861/870.
16. **Дисковая структура не была частью сквозного контракта.** Даже корректный
    генератор оставался непонятным в UI, когда источник жил в произвольном
    Downloads, производный файл — в другом каталоге, а SQLite помнила старый
    путь. Исходные MXL/MID/MP3/PDF теперь сведены в §7.4, производный MXL
    создаётся внутри того же комплекта, а кнопка строки ведёт непосредственно к
    визуальному стану и действиям сборки.
17. **Сокращённые данные анализа ошибочно приняли за нотацию.** Кастомный
    `FingeringStaff.vue` пытался заново вывести стан из `staffNotes`, поэтому
    неизбежно терял MusicXML-семантику beams, tuplets, нескольких voices,
    cross-staff, лиг и реальных издательских отступов. Результат выглядел как
    схематический график и создавал коллизии цифр в аккордах. Теперь API
    возвращает полный `previewXml`, а `FingeringScore.vue` отдаёт его OSMD —
    специализированному MusicXML-гравировщику.
18. **Corpus bench не отделял вход от собственного выхода.** Рекурсивный обход
    заходил в `fingered/`, после чего rebuild сравнивался с ранее созданными
    цифрами той же модели. Это не дополнительный тест, а leakage, способный
    тихо улучшать метрику после каждого прогона. Source-only фильтр и раздельные
    агрегаты дают честные 73,6 % по человеческому `<technical>` gold.
19. **Вторичная диагностика заняла место главной задачи.** Список одной и той
    же фигуры по каждому такту и десятки warnings вытесняли партитуру, а
    пользователь не понимал, как перейти к нужному такту. Нотный лист теперь
    доминирует; есть слайдер, prev/next, прямой ввод и клавиатура; паттерны
    агрегируются, диагностика и trace свёрнуты.
20. **Typography аппликатуры не была частью контракта.** Одна лишь
    `placement="above|below"` оставляла цифры слишком крупными и визуально
    плотными, а абсолютные координаты могли бы сломать раскладку другого
    нотатора. Auto-цифры теперь получают `font-size=8`, `relative-y ±2` без
    `default-x/default-y`; авторская типографика остаётся нетронутой.
21. **Objective cost не является понятной ученической метрикой.** После
    исправления формулы крупные отрицательные приоры закономерно дали
    отрицательные `costPerNote` на гаммах и Hanon. Это корректно для DP, но
    визуально похоже на «отрицательную сложность». UI теперь выводит
    эргономику основной цифрой, педагогическую скидку/надбавку — отдельной
    меткой, а bench сохраняет все три компонента.
22. **Межголосовой release оказался безусловной гипотезой о педали.** На
    Gymnopédie это совпадало с издательской практикой, но первая версия не
    читала `<pedal>` и одинаково оценивала верхний и нижний голос. Исправление
    добавило timeline и роль слоя, no-pedal polyphony gold и только затем
    сохранило высокий корпусный coverage; одна полнота сама по себе не была
    доказательством музыкальной корректности.
23. **«Собрать файл» и «обновить существующую композицию» — разные
    транзакции.** Прежняя CTA останавливалась после записи локального
    `fingered/*.mxl`, а строковое «Обновить» пересобирало только learning.
    Новый контракт §8.4 различает original/fingered, подтверждает фактический
    path и лишь затем разрешает перестройку учебного режима.
24. **Статическая легенда не описывает выбранный такт.** Подпись про триоль
    показывалась даже там, где крупной `3` нет, а реальные педаль, фермата,
    реприза или локальная альтерация оставались необъяснёнными. Теперь inventory
    строится из действующих и печатных MusicXML-элементов конкретного такта;
    неизвестный знак маркируется нейтрально, без музыкальной догадки. Первая
    динамическая версия всё ещё читала только узлы выбранного такта и потому
    теряла середину длинных wedge/pedal/octave-shift/dashes/bracket/slur/tie.
    Stateful scan start→middle→stop закрыл этот разрыв; счёт одновременно
    приведён к произносимой учеником форме `Раз-и`, а не технической `1-и`.
25. **Технический `voice` ошибочно вынесли в ученический интерфейс как готовое
    понятие.** В MusicXML это идентификатор независимого временного слоя, а не
    обязательно «голос певца», рука или нотоносец. UI называет его
    «мелодической линией», даёт короткое определение и сохраняет отдельные
    длительности/пальцы у двух линий с общей унисонной головкой.
26. **Ключевые знаки принимались за однозначную тональность.** Одинаковая
    сигнатура принадлежит мажору и относительному минору; без `<mode>` выбрать
    один лад по виду бемолей теоретически нечестно. Новый слой показывает
    порядок знаков и оба кандидата по квинтовому кругу, а точное название даёт
    только при явном mode/tonic.
27. **Проверка свободного пути не является защитой от параллельной записи.**
    Два MuseScore-job могли одновременно увидеть пустую папку композиции и
    смешать MXL одной редакции с MIDI/MP3 другой. Теперь каталог занимается
    exclusive lock-файлом; reconcile переносит комплект как пакет и откатывает
    уже перенесённые файлы при ошибке.
28. **Ритмический счёт сначала выглядел как техническая таблица.** Одинаковые
    подписи повторялись в каждом такте, полудоли жили в отдельных высоких
    карточках, а intrinsic width слова «Четыре» раздвигал grid и обрезал правый
    край окна из пяти тактов. Такой UI сообщал данные, но не учил действию.
    Попытка вылечить это flex-раскладкой 3/2/1 всё равно оставила пять полных
    таблиц и снова сломалась на шестнадцатых Lumière. Четырёхролевой quorum
    показал архитектурную ошибку: обзор и обучение были смешаны. Теперь OSMD
    сохраняет реальный нотный контекст 1/3/5, navigator выбирает такт, а только
    одна учебная таблица получает полную ширину и вложенные колонки долей.
29. **Метрическая клетка ошибочно считалась одним взаимоисключающим
    состоянием.** Приоритет `attack > hold > rest` скрывал полифонию:
    в Lumière, такт 5, правая рука на «Четыре» держит две ноты и одновременно
    берёт ещё две. `RhythmHandState` теперь отдельно хранит `attackNotes`,
    `heldNotes`, rest и staccato; tooltip формулирует составное действие.
30. **Ключ, рука и стан были склеены.** F-clef автоматически становился левой
    рукой, любой другой — правой, хотя ключ определяет чтение высоты, а не
    исполнителя. Fallback теперь стабилен по верхнему/нижнему фортепианному
    стану; `placement=above/below` не принимается за семантику руки.
31. **Линия длительности переходила точную границу.** Сравнение `end >= cell`
    добавляло половину следующей клетки уже закончившейся ноте. Строгое
    перекрытие и regression-тест вернули конец линии на реальную границу.
32. **Нотированная длительность выдавалась за физическое удержание.** В первых
    тактах Lumière staccato-восьмые выглядели как длинные legato-линии.
    Артикуляция теперь даёт короткий хвост и явную инструкцию отпустить, а
    нотированная длительность остаётся отдельным фактом.
33. **Минимальная математическая сетка оказалась недостаточной учебной
    сеткой.** Для целой ноты алгоритм выбирал четыре позиции и визуально
    превращал её в одно «Раз». Минимум простого метра теперь — восьмые:
    `Раз-и-Два-и-Три-и-Четыре-и`, одна атака и непрерывное удержание.
34. **Аудио могло тихо подменить инструмент.** При ошибке MP3 версия с
    осцилляторным fallback продолжала играть синтезатором, хотя CTA обещала
    Grand Piano. Теперь локальные Salamander samples обязательны: при ошибке
    проигрывание не стартует и UI показывает понятный диагноз.
35. **Активный учебный такт ошибочно подменил выбранный диапазон партитуры.**
    Первая версия overview привязала `drawFrom/UpToMeasureNumber` к одному
    active measure, поэтому кнопки 3/5 визуально ничего не меняли. Диапазон
    OSMD снова берётся из `measureWindowRange`, а active state управляет только
    detail, tooltip и проигрыванием. Временные ключи нот хранят сквозное
    смещение такта, поэтому START в такте 2 не подсвечивает такт 1.
36. **Tooltip сообщал только момент атаки, а не длительность счёта.** Для целой
    ноты строка `Счёт: Раз` была формально верной как onset, но педагогически
    скрывала семь следующих позиций удержания. Теперь tooltip строит count-span
    по тем же `RhythmCountItem`, что и таблица: целая в 4/4 показывает
    `Раз-и-Два-и-Три-и-Четыре-и`. Одновременно необъяснимое
    транслитерированное `е` из `1-e-&-a` заменено единым русским
    `Раз-та-и-та`.

Общий урок для следующих фаз: каждое требование проходит цепочку
**наблюдаемый инвариант → сквозной тест → только затем отметка «реализовано»**.
Именно отсутствие этой цепочки, а не ошибочность базовой модели, делало первую
версию PRD и реализации чрезмерно уверенной.

## 14. Что сознательно НЕ делаем

- **Обучаемые модели** (HMM/нейросети из Nakamura 2020, Ramoneda 2022). Они
  дают +5–7 % совпадения с эталоном, но требуют датасета PIG (лицензия только
  для академического использования), тренировки и рантайма. Для локального
  инструмента правило-ориентированная модель прозрачнее, детерминирована и
  объяснима: каждая цифра трассируется до конкретного правила.
- **Полный вывод педализации и общее перераспределение вертикалей между
  руками.** Текущая модель читает существующую `<pedal>` и умеет единственный
  локальный cross-hand edge transfer только при одном физически допустимом,
  неавторском и не-legato решении. Она не добавляет педаль, не переписывает
  `<staff>`/партии и не пытается произвольно переоркестровать неоднозначный
  аккорд между руками.
- **Оптимизацию под конкретного ученика** (реальный размер руки, травмы).
  Размер руки заложен в модель как множитель, но в UI на первом релизе не
  выносится.

## 14а. Ревизия «скорость и повторение» (§6.11–6.13)

Ревизия закрывает три разрыва, которые проявились на быстрых остинатных
пьесах (Clocks, ♩=132 восьмыми) и на любых фигурах с двузвучиями.

### 6.11 Реальное время вместо длительности

Модель Parncutt откалибрована на медленных одноголосных фрагментах и темпа не
знает. До ревизии его не знал и весь конвейер: единственная зависимая от
длительности константа `fastRepeat` задана в четвертях. Из-за этого хорал при
♩=40 и остинато при ♩=132 оценивались одинаковой целевой функцией.

Теперь `parseScore` читает темп из `<sound tempo>` и из `<metronome>`
(с пересчётом `beat-unit` и точек), событие руки получает `ipiBefore` —
реальные секунды до предыдущей атаки, — а шаг поиска взвешивается
`tempoWeights(base, ipi)`. Множитель `referenceIpi / ipi` ограничен сверху
(`maxScale = 3`) и снизу единицей. Правила движения (`sameFinger`,
`positionChange*`, `thumbPassing`, `handShift`) берут его целиком; правила позы
(растяжения, `weakFinger`, чёрные клавиши) — корень из него: удерживаемая поза
дорожает от скорости медленнее, чем перемещение. При отсутствии темпа
множитель равен 1, и поведение в точности прежнее.

Отчёт (`ergonomicCostPerNote`) намеренно считается базовыми весами, чтобы
метрика оставалась сравнимой между ревизиями.

### 6.12 Перенос кисти (`handShift`)

Правила 4 и 5 смотрят на тройку нот и не видят медленного дрейфа руки. Новая
статья цены считает «виртуальное положение большого пальца» —
`midi ∓ (maxRel(1,f) + minRel(1,f)) / 2` — и берёт его смещение сверх допуска
в 2 полутона. Перекладывание большого пальца исключено: подкладывание уже
оплачено правилом 12, а двойной штраф ломает школьный канон гамм.

Допуск выбран не по метрике: замер тянет его к нулю (0.8583 против 0.8533),
но нулевой допуск ломает альбертиев бас (5-1-3-1 проигрывает 5-1-2-1). Канон
важнее пяти сотых процента.

### 6.13 Повторяющиеся фигуры: `fingering-motifs.ts`

Прежний детектор остинато требовал 3–4 разные высоты, аккордовый корень и
поток одиночных нот, а форму руки брал из зашитой таблицы `[1, 2|3, 5]`.
Двузвучие внутри фигуры обнуляло распознавание целиком, и остаток пьесы
возвращался к локальным тай-брейкам: одна и та же вертикаль получала 3, 4 и 5
в соседних тактах.

Новый слой не содержит ни одного музыкального шаблона:

1. **Самоподобие.** Событие сводится к сигнатуре — набору высот (одинаково для
   ноты и для аккорда). Циклы ищутся жадно, период 2…8, минимум два полных
   повтора; неполный хвост последнего проведения включается в фигуру.
2. **Согласование, а не выбор.** Слой работает вторым проходом. Аппликатуру
   выбирает полноконтекстный beam-поиск; из форм, которые он ФАКТИЧЕСКИ
   поставил на разных проведениях, отбирается одна на всю фигуру — по цене
   оборота (включая возврат из последнего события в первое) с темповыми
   весами. Кандидаты ограничены наблюдёнными формами, поэтому слой не может
   породить хват, которого поиск не считал разумным.
3. **Непрерывность общих тонов.** Если соседние фигуры делят высоту, смена
   пальца на ней штрафуется (`MOTIF.continuity = 6`). Это переводит цепочку
   Clocks из «5-2-1 / 5-3-1» (кисть перекладывается каждый такт) в
   «5-2-1 / 4-2-1 / 4-2-1 / 5-3-1» — общий B♭ держит один палец, движется
   только край хвата.
4. **Приоритет.** Школьные фигуры (гамма, арпеджио, альбертиев бас,
   аккомпанемент) со своим приором не перекрываются. Наоборот, короткий
   обрывок арпеджио внутри измеренного повтора уступает общему слою:
   повторение — более сильное свидетельство, чем совпадение трёх нот с формой.

**Измеренная альтернатива, отвергнутая.** Первая версия отдавала выбор формы
изолированному оптимизатору цикла. Согласие падало (Hanon 0.767 → 0.741),
потому что цикл не видит контекста вокруг себя. Зафиксировано в комментарии
модуля, чтобы решение не переоткрывали.

### 6.14 Перенос формы против мелодической линии

`horizontalParts` не штрафовал повтор пальца между многозвучными событиями:
последовательность октав действительно играется переносом формы. Проверка
`polyphonic` объявляла переносом любую пару, где хоть одно событие многозвучно.
Выдержанный бас под движущимся верхом попадал под то же исключение, и линия
получала 3-3-2 вместо связного 5-4-3-2.

Теперь исключение действует только для настоящего блочного переноса: все
голоса события смещены на один и тот же интервал относительно предыдущего.
Неподвижный нижний голос сам по себе переносом не считается.

### 6.15 Повтор пальца обманывал правила 4 и 5

Найдено аудитом по всему корпусу (детектор физических дефектов, а не
расхождений с эталоном). `positionChangeCosts` сравнивает интервал между
крайними нотами тройки с комфортным диапазоном пары (f1, f3). Если внутри
тройки палец повторяется, этот диапазон ничего не значит: один палец дотянется
куда угодно, если руку переставить. Правило же честно рапортовало «смены
позиции нет» — и тем **поощряло** повтор.

Последствие видно на одноктавном арпеджио A-C-E-A (Cornfield Chase, т.17,
шестнадцатые): школьное 1-2-3-5 платит за раскрытие кисти, а абсурдное
1-1-2-5 не платит ничего и выигрывает, несмотря на 16 очков `sameFinger`.

Теперь тройка с повтором пальца на разных клавишах считается сменой позиции
размером в пройденное расстояние (диагональ матриц равна нулю, поэтому весь
переезд и есть превышение комфорта). Скольжение с чёрной на белую исключено.

### 6.16 Повторы на расстоянии

`consolidateMotifs` выравнивает смежные проведения. Тот же такт, вернувшийся
через страницу, решался заново и расходился на доли очка — в корпусе таких мест
было 138. `consolidateRecurrences` — третий проход по той же схеме: отрезки
(такты руки) группируются по совпадению сигнатур, среди вариантов, которые
поиск уже поставил, выбирается один по суммарной цене всех проведений вместе
с входом и выходом в каждое. Участки со школьным приором не трогаются.

### 6.17 Достижимость повтора проверялась только под лигой

`transitionFeasible` объявляет повтор пальца на другой клавише невозможным,
если это не повтор ноты и не скольжение с чёрной на белую. Но спрашивал об
этом только код лиги; в остальных местах повтор просто оценивался в 8 очков
(правило Jacobs) — и покупался, когда обход стоил дороже. В результат
попадали переходы, которые сама модель считает нереальными.

Clocks, т.34: фигура C#5–B♭4–F4 идёт хватом 4-2-1, но первая C#5 несёт сверху
A♭5. Аккорд брался как 2+5, и второй палец должен был за 227 мс перепрыгнуть
с C#5 на B♭4. С проверкой аккорд становится 3+5 — растяжение на пределе
`MaxPrac(3,5) = 7`, зато хват фигуры сохраняется, и линия идёт без разрывов.

Проверка мягкая. Жёсткий запрет физически честен, но опустошает луч поиска:
526 нот корпуса оставались вовсе без цифры. Поэтому конечный штраф
`UNREACHABLE_REPEAT`, соразмерный удвоенной цене законной смены позиции.
Широкий скачок (шире квинты рука переносится целиком), скольжение и перенос
всей формы руки в параллельном движении под правило не попадают.

### Замер ревизии

Две независимые метрики, обе воспроизводимые:

```
bun run bench:fingering -- <каталог>   # согласие с авторской разметкой
bun run audit:fingering -- <каталог>   # физические дефекты по всем пьесам
```

Первая — согласие с авторской аппликатурой,
`bun run bench:fingering` (микро-среднее по 2032 размеченным нотам):
**0.8440 → 0.8455**.

| файл | было | стало |
|---|---|---|
| Hanon, упражнения 1–30 | 0.7555 | 0.7498 |
| гаммы (Simone dagli Orti) | 0.9862 | 0.9793 |
| Indila, Love Story (♩=180) | 0.5631 | 0.6408 |
| Ed Sheeran, Bad Habits | 0.6667 | 0.6667 |

Вторая — физические дефекты по всем 25 пьесам корпуса (`fingering-audit.ts`).
Она важнее: согласие меряется по четырём файлам, половина которых — Hanon,
чья печатная аппликатура является тренировочной условностью, а не оптимумом.
Детекторы аудита физические, а не подогнанные: повтор пальца в мелодической
линии там, где рука обязана стоять; перекрещивание пальцев в вертикали;
чередование слабой пары быстрее 110 мс; большой на чёрной быстрее 130 мс;
одинаковый материал с разной аппликатурой. Аудит поймал повтор большого
пальца в арпеджио (§6.15), который бенчмарк не видел вовсе.

| дефект | было | стало |
|---|---|---|
| повтор пальца в мелодической линии | 780 | **88** |
| одинаковые такты — разная аппликатура | 138 | **74** |
| слабая пара 3-4/4-5 быстрее 110 мс | 10 | 12 |
| большой на чёрной быстрее 130 мс | 8 | 8 |
| нот без цифры | 21 | 60 |

Промежуточные замеры: §6.13 (до §6.15) — согласие 0.8533 при 780 и 138
дефектах; §6.15–6.16 — 0.8455 при 322 и 71. Каждое правило стоит несколько
тысячных согласия, целиком на Hanon, и снимает сотни физически неиграбельных
мест. Обмен принят сознательно: согласие меряется по четырём файлам, а
неиграбельность — свойство результата.

Плата за §6.17 — 39 дополнительных нот без цифры (21 → 60 на ~30 000):
там, где недостижимый повтор был единственным выходом, событие честно
помечается как неразрешённое вместо того, чтобы печатать невыполнимое.

Три прохода утраивают время подбора (7.6 → 19.3 с на 25 партитур).
